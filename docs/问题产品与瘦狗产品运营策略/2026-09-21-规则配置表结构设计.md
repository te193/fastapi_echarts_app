# 产品动作规则配置表结构设计

更新：2026-09-21。状态：设计稿，未连接MySQL执行建表。本版按“规则表只保存具体动作”的要求修订，替代此前包含路径、护栏、复盘等独立规则的设计。

## 1. 表的用途与一行的含义

表名：ops_product_rule_config。

一行定义：什么产品、什么执行对象、满足哪些条件后，产生什么具体动作，以及如何算出目标值。

例如“问题产品当前价高于P25，降至P25”是一条动作规则；“价格不得低于P10”只是动作条件，不单独建规则；“进入低销量路径”“通过预算检查”“D+7复盘”均不入本表。

本表只存动作定义，实际产品命中结果由后续调价动作表、广告动作表承接。配置里的规则编号、版本、草稿状态均是维护信息，不是产品标签。

## 2. 本次删除与保留

| 内容 | 本次处理 |
|---|---|
| 提价、降价、调bid、加精准、否词/否定商品、开启广告 | 保留为动作规则 |
| 问题产品预算调整 | 保留原文动作草稿，名额/执行边界未明确前不发布 |
| 样本筛选、角色路径 | 放在数据准备与计算流程，不入动作配置表 |
| 价格底线、毛利、TACOS、库存和预算限制 | 必要条件并入对应动作条件或统一输入检查，不单独保存为规则记录 |

## 3. 字段分组

具体类型、长度、中文注释和索引见配套SQL。

| 字段组 | 字段 | 用途 |
|---|---|---|
| 身份与版本 | id、rule_set_code、rule_set_version、rule_code | 稳定编号及完整动作配置版本 |
| 名称与说明 | rule_name、rule_description | 说明该动作条件；不作为产品筛选标签 |
| 适用对象 | product_role、object_type、scope_json | 问题/瘦狗、产品/自动对象/手动词/搜索词、七国等范围 |
| 动作条件 | condition_json、required_fields_json | 完整条件及必需输入；缺数据不生成数值动作 |
| 动作输出 | action_type、calculator_code、parameter_json | 固定动作类型、计算模板、涨跌幅/底线/精度等参数 |
| 动作选择 | exclusive_group、priority | 同一物理对象上的互斥组及同方向档位优先级 |
| 可解释性 | reason_template、source_refs_json | 生成可读原因，追溯原文章节与源文件摘要 |
| 配置维护 | resolution_status、resolution_note、status | 已映射/待明确/暂缓，草稿/发布/退役；仅配置维护使用 |
| 生效与审计 | effective_from、effective_to、definition_hash、created_by、updated_by、created_at、updated_at | 版本生效及定义追溯 |

不再出现common角色或none动作类型。每条已发布记录必须指向一个明确动作类型。object_type=ad_object表示同一模板支持自动和手动对象，具体对象身份与各自取整方式仍需明确。

## 4. 条件与计算示例

问题产品“最多降5%，不低于P10”的业务主体配置示例：

```json
{
  "rule_code": "100102",
  "rule_name": "问题产品区间内受控降价",
  "rule_set_code": "product_operation",
  "rule_set_version": "v2_draft",
  "product_role": "problem",
  "object_type": "product",
  "scope_json": {"country_codes": ["DE", "FR", "IT", "ES", "NL", "UK", "US"]},
  "condition_json": {
    "all": [
      {"field": "eligible_problem_product", "op": "eq", "value": true},
      {"field": "price_action_due", "op": "eq", "value": true},
      {"field": "price_inputs_valid", "op": "eq", "value": true},
      {"field": "daily_sales_30d", "op": "lte", "value": 1},
      {"field": "current_price", "op": "gt", "value_field": "p10"},
      {"field": "current_price", "op": "lte", "value_field": "p25"}
    ]
  },
  "required_fields_json": [
    "eligible_problem_product", "price_action_due", "price_inputs_valid",
    "daily_sales_30d", "current_price", "p10", "p25", "currency_code", "currency_precision"
  ],
  "action_type": "price_decrease",
  "calculator_code": "reduce_with_floor_v1",
  "parameter_json": {"reduce_rate": 0.05, "floor_field": "p10", "rounding": "currency_ceiling"},
  "exclusive_group": "price_change",
  "priority": 20,
  "reason_template": "当前价{current_price}高于P10且不高于P25，按5%降幅和P10底线建议调至{suggested_price}",
  "resolution_status": "mapped",
  "status": "draft"
}
```

示例省略维护人、原文章节摘要等导入字段，不是完整初始化记录。eligible_problem_product是样本与退出状态计算结果，price_action_due表示首轮或经真实执行历史允许的下一轮，price_inputs_valid表示价格质量及必要执行前提通过；这些是输入字段，不是规则记录或标签，其口径需要在后续数据开发中固定。未决断货价格口径未解决前不得把price_inputs_valid默认置true。

条件只允许all/any/not及eq/ne/gt/gte/lt/lte/in/is_null/is_not_null。普通比较遇到缺失值为unknown，不能当0或false；not unknown仍未知。字段、操作符和模板使用白名单，不允许执行任意SQL或代码。

比例统一存小数，金额与bid按明确精度计算。模板只负责有限计算，例如设为模型价格线、按比例降价且守底线、调bid、计算初始精准bid。新增算法升级模板版本，单纯阈值调整升级配置版本。

## 5. 保证最终结果可筛选

最终用户按固定动作类型筛选：降价、提价、降低竞价、提高竞价、新增精准词、否定关键词、否定商品、开启广告。问题产品预算调整仍是未发布草稿，明确后再纳入。

不按规则编号、命中条件、涨跌幅、路径、库存等级或复盘时点扩展标签。

例如一个产品满足“低销量、毛利条件、预算可用、库存可承接、关键词有效”，最终选中一个关键词提高竞价5%。广告表只写一条bid_increase，目标bid与原因写在详情；不会同时写五条条件标签。

同一产品若真实需要“降价+降低某对象竞价+否定某词”，仍可有三条不同具体动作，这符合原文1个价格+最多2个广告的上限。用户要求是避免过程标签混入，不是强行将所有真实操作压成一个标签。后续产品日汇总按action_type去重，具体对象在动作明细展示。

多个规则命中同一对象同一动作时，先完成基础档选择、限幅及互斥，再只输出一条最终动作。rule_code作为证据字段，可记录主命中及解释，但不自动生成标签。

## 6. 数据处理职责

1. 数据准备：识别七国当期产品，补齐销量/毛利/价格/广告/库存/预算/执行历史。
2. 动作计算：加载指定完整版本的动作规则，检查完整条件，计算候选目标值。
3. 统一选择：有效止损优先；同对象涨降冲突、同词新增与否定冲突、数量上限和共享预算占用统一处理。
4. 结果落表：只保存最终选中的具体动作；未命中和阻断原因写运行诊断。
5. 复盘任务：使用真实生效时间检查效果，必要时产生新一轮具体动作，不输出复盘标签。

非动作逻辑继续保留在原业务文档和后续数据处理程序中。本次没有再为它们新增一张“过程规则配置表”。从动作表无法完整统计全部被阻断产品，后续查询诊断需读取对应运行明细。

## 7. 版本、索引与交付状态

唯一键：rule_set_code + rule_set_version + rule_code。动作集按版本整体加载，禁止逐条取最新版本拼接。初始配置保持draft；已发布业务定义不原地改写，修改生成新版本，整版生效由发布程序控制。

索引围绕版本、发布状态、产品角色、动作类型加载；JSON用于可变条件与参数，关键查询字段保留普通列。SQL以MySQL 8.x、InnoDB为设计目标，实际服务器版本与schema尚未核验。

当前清单保留52个动作分支，问题产品26个、瘦狗产品26个，包含本次明确的开启广告建议。该数字是业务拆解行数：正式初始化时，文字/ASIN对象和不同最终涨幅可能需拆成多条完整配置，但不会增加动作标签种类。

原始策略文档保持不变。本次仅修订设计、SQL草稿和业务拆解清单，未创建数据库表，未导入或发布配置。


## 动作规则编码约定

固定六位：`RMMMSS`，即角色1位＋模块3位＋序号2位。`100101`拆为`1 / 001 / 01`，表示问题产品、调价模块、第01条动作。该划分取代其他临时位数描述。

| 编码段 | 含义 | 取值 |
|---|---|---|
| 第1位R | 产品角色 | 1=问题产品；2=瘦狗产品；其余保留，新增角色时登记 |
| 第2—4位MMM | 动作模块 | 见下表，跨角色保持相同含义 |
| 第5—6位SS | 模块内动作序号 | 01—99；00保留；序号不表示优先级 |

| 模块代码 | 模块名称 | 问题产品示例 | 瘦狗产品示例 |
|---|---|---|---|
| 001 | 调价 | 100101 | 200101 |
| 002 | 自动投放竞价 | 100201 | 200201 |
| 003 | 手动关键词竞价 | 100301 | 200301 |
| 004 | 自动/手动通用竞价扩量 | 当前未配置 | 200401 |
| 005 | 搜索词动作（加精准、否词/否定商品） | 100501 | 200501 |
| 006 | 零花费曝光测试 | 100601 | 200601 |
| 007 | 产品预算调整 | 100702，仍为待明确草稿 | 当前未配置 |
| 008 | 开启广告 | 100801 | 200801 |

模块是具体动作的分类，不新增护栏、路径或复盘规则。004用于原文中自动/手动共用的扩量分支；动作类型仍按action_type筛选，不能仅凭模块判断涨bid还是降bid。

存储使用`char(6)`，JSON中也使用字符串，例如`"rule_code": "100101"`。发布时校验六位数字、角色位与product_role一致、模块合法且序号01—99。版本变化不改规则编号；新增分支使用未占用序号，停用编号不复用。一个模块序号不足时登记新的细分模块，不延长编码或擅自换位数。

原有条目序号尽量保留，所以可能出现200103后接200106；这不表示缺失配置。I01等是文档待明确事项编号，不是动作规则编码，不改成六位数字。

## 第一版数据范围补充

本期优先基于当前最新可用数据产出可解释的动作建议，包括确认未开启广告时的“开启广告”。不以完成效果评估、第二轮优化、固定样本跟踪或完整经营闭环为第一版抽取前置条件。原文保留的复盘节奏属于后续工作；缺少历史执行回执时，不据此伪造二调、撤回或已完成复盘的结论。

“开启广告”使用ad_enable，产品粒度输出，当前对象ID可不适用；通过数据完整性检查后确认未开启才能命中，已开启零花费和映射待核均不能误判。无结构的新建、已有停用结构的启用由人工根据详情处理；输出建议不代表已执行，也不自行生成缺失的预算、bid或目标广告组参数。

规则中的当前毛利、TACOS、库存、预算等准入仍需判断。第一版不能因复盘后置就忽略这些限制；未明确的当前动作分支留待核，不擅自补阈值。护栏、路径和复盘仍不作为独立动作标签。
