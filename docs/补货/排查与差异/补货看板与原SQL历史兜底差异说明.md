# 补货看板与原 SQL 历史兜底差异说明

## 背景

本次对比使用的是修正可售天数后的原 SQL 导出文件：

- `E:\Data\sql导出数据\26-6\6.24\更改可售.csv`
- 看板本地表：`dashboard_pur_plan_replenish_data`
- 对比日期：`2026-06-24`

修正前原 SQL 的可售天数字段为空，导致大量 SKU 走历史兜底，数量被放大；修正后，可售天数、周期销量和日销口径已基本对齐。

## 核心数量

| 项目 | MSKU 数 |
| --- | ---: |
| 原 SQL 修正后最终输出 | 278 |
| 看板紧急/建议/计划三层合计 | 249 |
| 两边都包含 | 160 |
| 看板三层有、原 SQL 没有 | 89 |
| 原 SQL 有、看板三层没有 | 118 |

## 原 SQL 有、看板三层没有的 118 个

这 118 个并不是看板基础池缺失，全部能在看板当天全量结果里找到，只是没有进入紧急/建议/计划三层：

| 看板原始分层 | 数量 |
| --- | ---: |
| 库存充足 | 90 |
| 日销为0 | 28 |

其中按 `history_recovery_flag` 拆分：

| 类型 | 数量 | 说明 |
| --- | ---: | --- |
| `history_recovery_flag = 1` | 84 | 原 SQL 会因为历史恢复兜底条件输出；看板原始库存支撑分层里仍可能是库存充足或日销为0 |
| `history_recovery_flag = 0` | 34 | 主要是原 SQL 的 120 天缺货/触发量规则与看板当前库存支撑天数规则不同 |

`history_recovery_flag = 1` 的 84 个在看板原始分层中分布为：

| 看板原始分层 | 数量 |
| --- | ---: |
| 库存充足 | 56 |
| 日销为0 | 28 |

## 看板三层有、原 SQL 没有的 89 个

这部分主要不是日销或库存字段差异，而是最终进入补货计算的业务规则不同：

- 看板三层入口：按当前库存支撑天数分层，`<= 90 天` 进入紧急/建议/计划。
- 原 SQL 最终输出：除了补货判断外，还会看 120 天缺货量、触发量以及历史恢复兜底。
- 其中 88 个是看板进入了三层，但在原 SQL 中 `replenish_dur_calc_stocko_qty < replenish_trigger_qty`，所以未被原 SQL 最终输出。

## 字段层面对齐情况

修正可售天数后，重合的 160 个里这些关键字段已基本对齐：

- `daily_avg_sales`
- `final_sales_30d`
- `final_sales_14d`
- `final_sales_7d`
- `final_sales_3d`
- `replenish_dur_calc_stocko_qty`
- `available_total`
- `stock_up_num`
- `local_quantity`
- `sc_quantity_purchase_plan`

仍有少量差异集中在：

- `fba_local_quantity`
- `salable_days`
- `sales_adj_factor`
- `replenish_qty`

这些属于后续精细对齐项，不是本次 278 与 249 主差异的主要原因。

## 当前看板处理方式

为了让原 SQL 的历史恢复兜底 SKU 在看板上可见，同时不改动现有补货计算和落表结果，看板新增一个展示层：

`历史兜底`

展示口径：

```sql
history_recovery_flag = 1
and support_replenish_level_sort not in (1, 2, 3)
```

也就是说：

- 已经在紧急/建议/计划三层里的 SKU，仍保留原三层展示。
- 原始分层为库存充足或日销为0，但被原 SQL 历史恢复兜底输出的 SKU，会在页面单独显示为“历史兜底”。
- 数据库里的 `support_replenish_level` 不改写，只在 API/前端展示层做派生。

## 结论

现在的主要差异不是数据源错误，而是两个入口规则不同：

1. 看板按库存支撑天数做三层补货分层。
2. 原 SQL 会额外把历史恢复兜底 SKU 拉进最终输出。

因此，看板新增“历史兜底”展示层后，可以直接看到这批 SKU 数量，后续如果决定把历史兜底也纳入正式补货层判断，再单独调整计算逻辑。
