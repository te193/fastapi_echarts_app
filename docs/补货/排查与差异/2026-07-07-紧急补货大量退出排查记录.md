# 2026-07-07 紧急补货大量退出排查记录

## 1. 排查背景

2026-07-07 补货页面中，今日“紧急补货”数量相比前一日明显下降。业务侧观察到很多原本处于紧急补货的 MSKU 今日已经被推出紧急层级，需要确认：

- 是否真的因为库存、采购计划、在途等数据发生变化而退出；
- 还是远端数据源、本地同步或补货计算逻辑出现异常。

本次排查只看数据和计算链路，不修改代码、不重跑 ETL。

## 2. 当前补货分层核心口径

补货结果表：

```text
dashboard_pur_plan_replenish_data
```

核心字段：

| 字段 | 含义 |
| --- | --- |
| `cur_date` | 补货结果日期 |
| `support_replenish_level` | 补货层级文本，如紧急补货、建议补货、计划补货、库存充足、日销为0 |
| `support_replenish_level_sort` | 补货层级排序，1=紧急补货，2=建议补货，3=计划补货，4=库存充足，5=日销为0 |
| `inventory_support_days` | 库存支撑天数 |
| `support_inventory_qty` | 用于计算库存支撑天数的支撑库存数量 |
| `pre_daily_avg_sales` | 用于分层的日销 |
| `available_total` | FBA 可售库存 |
| `stock_up_num` | 备货/在途类库存 |
| `local_quantity` | 本地/采购相关数量汇总 |
| `sc_quantity_purchase_plan` | 采购计划数量 |

当前代码中，库存支撑天数的核心计算逻辑是：

```text
inventory_support_days = support_inventory_qty / pre_daily_avg_sales
```

其中：

```text
support_inventory_qty = available_total + stock_up_num + local_quantity
```

分层规则大致为：

| 支撑天数 | 分层 |
| --- | --- |
| 日销 <= 0 | 日销为0 |
| <= 35 天 | 紧急补货 |
| > 35 且 <= 65 天 | 建议补货 |
| > 65 且 <= 90 天 | 计划补货 |
| > 90 天 | 库存充足 |

所以，只要 `local_quantity` 明显增加，即使 FBA 可售库存没有增加，也会把 `support_inventory_qty` 和 `inventory_support_days` 拉高，从而导致 MSKU 从“紧急补货”退出。

## 9. 判断结论

综合结果表和源表校验，本次结论如下：

```text
按当前补货系统口径，这批 MSKU 今日退出紧急补货是“真实计算结果”，不是本地结果表缺数，也不是 ETL 没更新。
```

更准确地说：

```text
它们不是因为 FBA 可售库存真实入仓变多而退出，
而是因为补货快照源表今天给这些 MSKU 增加了采购计划/采购在途/本地相关数量，
这些数量被汇总进 local_quantity，
而 local_quantity 参与库存支撑天数计算，
所以导致层级从紧急补货退出。
```

因此，本次问题不是“数据源错了”这一类简单结论，而是需要确认业务口径：

```text
采购计划/采购在途/本地数量是否应该参与紧急补货分层的库存支撑计算。
```

## 10. 需要业务确认的问题

后续建议先确认以下口径，再决定是否改代码：

### 10.1 采购计划是否应该让 MSKU 退出紧急补货

如果采购计划只是“计划建了”，但还未采购、未发货、未入仓，那么它是否应该增加库存支撑天数？

当前系统口径是：

```text
会参与。
```

如果业务认为采购计划不应该让紧急补货退出，那么需要从 `support_inventory_qty` 中剔除采购计划数量，或至少降低其权重。

### 10.2 采购在途是否应该让 MSKU 退出紧急补货

采购在途比采购计划更接近真实库存，但仍未到 FBA。需要确认：

- 采购在途是否全量计入支撑库存；
- 是否按预计到货时间折扣；
- 是否只对“建议补货/计划补货”有影响，不直接解除紧急。

### 10.3 本地可用、质检、采购计划是否应该分开对待

当前 `local_quantity` 是一个汇总口径，容易把不同状态的数量混在一起。

更细的业务口径可能是：

| 状态 | 是否计入支撑库存 | 说明 |
| --- | --- | --- |
| FBA 可售库存 | 应计入 | 已经可售 |
| FBA 备货/在途 | 可计入 | 当前已有 `stock_up_num` |
| 本地可用库存 | 可计入 | 需要确认是否能快速发 FBA |
| 本地质检库存 | 谨慎计入 | 还未完全可用 |
| 采购在途 | 可部分计入 | 可按到货周期折扣 |
| 采购计划 | 建议不全量计入 | 只是计划，风险较高 |

## 11. 后续优化建议

### 方案 A：保持当前口径

如果业务认可“采购计划/采购在途/本地数量都可以支撑库存”，则不需要修改。

优点：

- 逻辑简单；
- 能及时反映采购端动作；
- 已建计划后不会继续重复建议补货。

缺点：

- 采购计划一建立，低日销 SKU 的支撑天数可能被拉得非常高；
- 紧急补货会过早退出；
- 页面上看起来像“突然库存充足”，但实际 FBA 未必充足。

### 方案 B：紧急分层只看 FBA 可售 + 真实在途，不看采购计划

将 `support_inventory_qty` 调整为：

```text
available_total + stock_up_num + 本地可用库存 + 采购在途
```

不计入：

```text
purchase_plan_quantity
```

优点：

- 避免只建了采购计划就退出紧急；
- 更符合“库存支撑”的保守口径。

缺点：

- 已建采购计划的 SKU 可能仍然留在紧急补货里；
- 需要用追踪状态辅助判断“已处理但未解除”。

### 方案 C：采购计划参与补货数量扣减，但不参与分层支撑

也就是分两套口径：

```text
分层支撑库存 = FBA 可售 + stock_up_num + 本地可用/在途
补货数量扣减 = FBA 可售 + stock_up_num + local_quantity + purchase_plan_quantity
```

优点：

- 分层更保守；
- 补货数量不会重复建议太多；
- 可以同时表达“仍紧急，但已有采购计划覆盖一部分”。

缺点：

- 口径比现在复杂；
- 前端需要解释“分层”和“补货数量”为什么使用不同库存口径。

### 方案 D：增加“已建采购但仍紧急”状态

保留紧急补货分层，但在页面上增加状态标签：

```text
紧急补货 / 已建采购
紧急补货 / 采购在途
紧急补货 / 未处理
```

优点：

- 不会让采购动作直接把 SKU 推出紧急；
- 又能看到采购端是否已经处理；
- 适合和补货追踪联动。

缺点：

- 前端和接口展示需要增加字段；
- 需要明确每个状态的计算规则。

## 12. 本次排查最终结论

本次 2026-07-07 紧急补货从 61 个下降到 14 个，主要原因是：

```text
补货快照源表 dashboard_restock_daily_snapshot 中，今日大量 MSKU 的 local_quantity 增加。
这些 local_quantity 主要来自 purchase_plan_quantity 和 purchase_shipping_quantity。
当前补货分层把 local_quantity 计入 support_inventory_qty。
因此库存支撑天数被显著拉高，导致很多 MSKU 从紧急补货退出，尤其是进入库存充足。
```

所以：

```text
按当前代码和当前业务口径，结果是合理的；
但如果业务认为采购计划/采购在途不能直接解除紧急补货，则需要调整补货分层口径。
```

建议下一步：

```text
先确认采购计划、采购在途、本地库存分别是否参与“紧急补货分层”。
确认后再决定是否改 support_inventory_qty 的组成，或增加“已建采购但仍紧急”的独立状态。
```
