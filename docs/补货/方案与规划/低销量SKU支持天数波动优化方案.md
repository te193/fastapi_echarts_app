# 低销量 SKU 支持天数波动优化方案

## 背景

当前补货看板里，支持天数的核心口径是：

```text
支持天数 = 支撑库存 / 计算日销
```

对正常销量 SKU，这个口径比较直观。但对低销量 SKU，尤其是 30 天只卖 1-3 件的商品，短周期内多出 1 单会让 3 天、7 天、14 天窗口销量同时变化，导致计算日销突然放大，支持天数从几百天跳到几十天。

例如 `DY-057a`：

```text
前一天：支撑库存 4，计算日销 0.006667，支持天数 600
当天：支撑库存 3，计算日销 0.113333，支持天数 26.47
```

根因不是数据错误，而是低销量 SKU 的短周期样本太少，1 单对日销权重影响过大。

## 方案一：低销量 SKU 降低短周期权重

### 方案说明

当 SKU 满足低销量条件时，不再使用当前老品的短周期高权重公式。

当前老品公式类似：

```text
日销 = 7天日销 * 0.6 + 14天日销 * 0.2 + 30天日销 * 0.2
```

低销量 SKU 可以改成更偏长期窗口：

```text
日销 = 7天日销 * 0.2 + 14天日销 * 0.2 + 30天日销 * 0.6
```

低销量条件可以是：

```text
30天销量 <= 3
```

或：

```text
30天日销 < 0.2
```

### 例子

某 SKU 30 天销量 2 件，最近 7 天刚卖 1 件：

```text
7天日销 = 1 / 7 = 0.1429
14天日销 = 1 / 14 = 0.0714
30天日销 = 2 / 30 = 0.0667
```

原公式：

```text
0.1429 * 0.6 + 0.0714 * 0.2 + 0.0667 * 0.2 = 0.1133
```

新公式：

```text
0.1429 * 0.2 + 0.0714 * 0.2 + 0.0667 * 0.6 = 0.0829
```

如果支撑库存是 3：

```text
原支持天数 = 3 / 0.1133 = 26.47 天
新支持天数 = 3 / 0.0829 = 36.19 天
```

### 能达到的效果

可以降低单日 1 单对低销量 SKU 的冲击，让支持天数变化更平滑。

### 代价和风险

如果某个低销量 SKU 真的开始起量，模型反应会稍慢。

## 方案二：低销量 SKU 分层加防抖

### 方案说明

不直接改日销公式，而是在补货分层上加防抖规则。

例如：

```text
如果 30天销量 <= 3：
  支持天数 <= 35 不立即进入紧急补货
  需要连续 2 天支持天数 <= 35
  或最近 7 天销量 >= 2
```

### 例子

某 SKU 昨天支持天数 600，今天因为卖了 1 件变成 26。

如果使用原规则：

```text
26 <= 35，进入紧急补货
```

加防抖后：

```text
30天销量 = 2
最近7天销量 = 1
昨天不是紧急
今天先进入观察或计划补货
```

如果明天支持天数仍然低于 35，或最近 7 天销量变成 2 件，再进入紧急补货。

### 能达到的效果

可以防止低销量 SKU 因为单日 1 单，从库存充足直接跳到紧急补货。

### 代价和风险

需要依赖前一天结果，逻辑会比纯当天计算多一层历史状态判断。

## 方案三：低销量 SKU 单独归类为观察补货

### 方案说明

对低销量且库存不高的 SKU，不直接归入紧急、建议、计划、库存充足，而是增加一个中间状态：

```text
低频观察
```

示例条件：

```text
30天销量 <= 3
且 支撑库存 <= 5
且 计算日销 < 0.2
```

### 例子

某 SKU：

```text
30天销量 = 2
支撑库存 = 3
计算日销 = 0.1133
支持天数 = 26.47
```

原逻辑：

```text
支持天数 <= 35，紧急补货
```

新逻辑：

```text
命中低频观察，不直接进紧急补货
```

### 能达到的效果

让低销量商品和正常动销商品分开管理，避免补货人员把低频商品误认为真实紧急缺货。

### 代价和风险

需要页面、筛选、统计口径都接受新增状态，否则看板分类会变复杂。

## 方案四：低销量 SKU 支持天数封顶或托底

### 方案说明

计算日销和原始支持天数仍然保留，但用于分层时增加低销量保护。

例如：

```text
如果 30天销量 <= 3 且 最近7天销量 <= 1：
  分层支持天数 = max(当前支持天数, 稳定支持天数)
```

稳定支持天数可以来自 30 天日销、90 天有货日销，或历史低销量兜底口径。

### 例子

某 SKU：

```text
当前支持天数 = 26.47
按30天日销计算支持天数 = 45
按90天有货日销计算支持天数 = 27
```

如果选择 30 天日销作为稳定口径：

```text
分层支持天数 = max(26.47, 45) = 45
```

原逻辑：

```text
26.47，紧急补货
```

新逻辑：

```text
45，建议补货或观察
```

### 能达到的效果

在不改变原始日销展示的情况下，减少低销量 SKU 的分层误跳。

### 代价和风险

同一行会存在“展示支持天数”和“分层支持天数”两个口径，需要说明清楚。

## 方案五：按库存件数给低销量 SKU 单独分层

### 方案说明

对低销量 SKU，不再完全依赖支持天数，而是直接按库存件数判断风险。

示例规则：

```text
如果 30天销量 <= 3：
  支撑库存 <= 0：紧急补货
  支撑库存 1-2：建议补货
  支撑库存 3-5：计划补货或观察
  支撑库存 > 5：库存充足
```

### 例子

某 SKU：

```text
30天销量 = 2
支撑库存 = 3
支持天数 = 26.47
```

原逻辑：

```text
支持天数 <= 35，紧急补货
```

新逻辑：

```text
低销量 SKU，支撑库存 3 件，进入计划补货或观察
```

### 能达到的效果

对低频商品更直观。因为这类商品的“天数”本来不稳定，看还剩几件往往更符合采购判断。

### 代价和风险

件数阈值需要按品类或业务习惯确认，不能一刀切得太死。

## 方案六：引入销售置信度

### 方案说明

给每个 SKU 计算一个销售置信度，用来判断当前日销是否值得完全相信。

置信度可以由这些指标组成：

```text
30天销量
最近30天有销量天数
最近7天销量
近30天销量是否集中在单日
```

示例：

```text
30天销量 >= 5：高置信度
30天销量 2-4：中置信度
30天销量 <= 1：低置信度
```

低置信度商品即使支持天数低，也不直接进入紧急补货。

### 例子

某 SKU：

```text
30天销量 = 2
有销量天数 = 2
最近7天销量 = 1
支持天数 = 26.47
```

置信度判断：

```text
低置信度
```

分层结果：

```text
低置信度观察，而不是紧急补货
```

如果后续变成：

```text
最近7天销量 >= 2
或 30天销量 >= 5
```

再允许进入正常紧急/建议/计划分层。

### 能达到的效果

把“模型算出来的风险”和“这个风险是否可信”分开，解释性比较强。

### 代价和风险

需要新增置信度字段和页面展示，逻辑比简单规则复杂。

## 方案七：支持天数改成区间判断

### 方案说明

低销量 SKU 不只看一个支持天数，而是同时计算短期支持天数和稳定支持天数。

例如：

```text
短期支持天数 = 支撑库存 / 短周期加权日销
稳定支持天数 = 支撑库存 / 30天或90天日销
```

分层时看两个值是否都低。

### 例子

某 SKU：

```text
短期支持天数 = 26.47
30天稳定支持天数 = 45
90天稳定支持天数 = 27
```

如果规则是：

```text
短期和稳定都 <= 35，才进紧急
只有短期 <= 35，稳定 > 35，则进观察
```

那么这个 SKU 可以不直接进入紧急。

### 能达到的效果

可以把短期变化和长期稳定水平同时表达出来，适合解释“为什么今天突然跳了”。

### 代价和风险

看板会变复杂，补货人员需要理解两个支持天数口径。

## 方案八：拦截库存充足到紧急补货的单日大跳变

### 方案说明

不改日销，不改支持天数，只针对分层变化增加跳变保护。

示例规则：

```text
如果昨天是库存充足，今天是紧急补货：
  且 30天销量 <= 3
  且 今日销量 <= 1
  则今天不直接进入紧急补货
  先进入计划补货或观察
```

如果第二天仍然满足紧急补货，再正式进入紧急补货。

### 例子

某 SKU：

```text
昨天：库存充足，支持天数 600
今天：紧急补货，支持天数 26.47
30天销量 = 2
今日销量 = 1
```

原逻辑：

```text
直接从库存充足跳到紧急补货
```

新逻辑：

```text
命中单日大跳变保护，先进入观察或计划补货
```

如果明天仍然是：

```text
支持天数 <= 35
```

则解除保护，进入紧急补货。

### 能达到的效果

非常精准地解决“600 天到 27 天”这种跳变问题，对其他正常商品影响小。

### 代价和风险

需要依赖昨日分层结果。如果前一天数据缺失，规则需要有默认处理。

## 横向对比

| 方案 | 改动位置 | 稳定效果 | 对正常商品影响 | 解释成本 | 推荐程度 |
| --- | --- | --- | --- | --- | --- |
| 方案一：降低短周期权重 | 日销公式 | 中 | 中 | 中 | 可选 |
| 方案二：分层防抖 | 分层逻辑 | 高 | 低 | 中 | 推荐 |
| 方案三：低频观察分类 | 分层状态 | 高 | 低 | 中高 | 可选 |
| 方案四：支持天数托底 | 分层口径 | 中高 | 低 | 中高 | 可选 |
| 方案五：按库存件数分层 | 低销量分层 | 高 | 低 | 低 | 推荐 |
| 方案六：销售置信度 | 风险判断 | 高 | 低 | 中高 | 推荐但稍复杂 |
| 方案七：区间支持天数 | 展示和分层 | 中高 | 低 | 高 | 谨慎 |
| 方案八：单日大跳变拦截 | 分层变化 | 高 | 很低 | 低 | 推荐 |

## 初步建议

如果想要稳妥、改动少，可以优先评估：

```text
方案八：单日大跳变拦截
方案五：低销量 SKU 按库存件数分层
方案二：低销量 SKU 分层防抖
```

这三个方案都不需要大改日销计算本身，对现有正常商品影响较小，也比较容易向业务解释。

如果后续希望模型更完整，可以再考虑：

```text
方案六：销售置信度
```

它更系统，但需要多一个置信度字段和页面解释。
