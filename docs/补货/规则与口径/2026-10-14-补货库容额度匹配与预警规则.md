# 补货库容额度匹配与预警规则

状态：2026-10-14修订实现。本文为现行规则与交接入口；旧[库容数据定位与库存限制方案](2026-10-13-库容数据定位与库存限制方案.md)保留为来源调查和初版设计记录。

## 业务边界

补货页面、Excel及末尾“颜色与标注说明”Sheet只增加提示。所有销售角色参与；补货数量、箱数、货值、MOQ、销量计算、原有整行颜色及跟卖边框不变。默认生成补货当月开始发货流程。没有库容映射不清零数量，也不写入或重算远端数据。

## 月份与采集日期

- 库容主来源为`dwd_datasync.lx_replenishment_restriction`。读取`month=补货日期所在月第一天`、`snapshot_month=该月YYYY-MM`的明细，不跨历史采集月借用额度。
- 当前月读取该月最新保留版本，采集日期按上海当前日期校验，当天或前一天有效；更早则展示来源观察及日期待核原因。
- 历史月读取该月月底归档，按该月最后一天校验；未覆盖月底时说明归档不完整。月份内任一天的历史补货页面都明确注明“月末归档，不代表所选历史日的实时库容”。
- 当前月只留最新版本，查看该月较早补货日时也明确注明当前最新版本不能复原历史日；不因所选历史日的截止条件而把现存店铺额度过滤掉。
- `create_time`用于说明DWD采集日期；`source_update_time`保留平台更新时间，不能拿平台值未变化时的旧更新时间替代采集日期。
- 2026-10-14只读核查：DWD保留2026-08/09/10，采集日分别为8月31日、9月30日、10月13日，符合历史月底归档、当前月最新版本的留存结果。尚未核验外部采集程序的覆盖实现，不修改采集、表结构或保存策略。

## 店铺和额度匹配

1. 补货对象仍为国家类别＋店铺＋MSKU。按类别内的Basic Seller国家记录，优先精确匹配店铺完整名称/账号别名；没有精确匹配时，沿用补货ETL的`substring_index(seller_name,'-',1)`首段规则匹配Basic Seller的name。例如补货Tboke对应Tboke-eu-DE所属sid，而不是要求账号别名Tboke-eu等于Tboke。名称关联多个账号时单独报关联歧义，不做任意前缀模糊匹配，不猜测。[现行ETL来源](../../../etl/replenishment_update.py)的seller_name_new是此首段规则。
2. 欧洲匹配当前类别的欧洲国家，英国匹配英国，北美本期仅展示美国sid的额度，不混入加拿大和墨西哥。库容范围不套用低毛利标注的指定国家范围。
3. 直接读取该店铺自身sid的DWD额度，不要求该店铺出现在共享组快照。没有成功共享组批次或辅助共享组查询失败，也不提前退出额度读取。
4. 实际商品仓储类型优先读取`temporary_dwd.FBA库存明细.仓储类型`，按完整店铺名列表及MSKU关联，识别标准、大件、服装、鞋靴、超大件。同对象冲突不强行归类。实际类型缺失时，再用月仓储费Standard-Size/Oversize映射Standard/Oversize进行注明来源的估算，不再无条件要求人工确认。不能把普通/组合产品、新/老品等产品分类当作仓储类型。
5. 当前类别、当前账号的Standard共享组代表sid必须属于该店铺已匹配sid；满足时可选其DWD额度展示。额度数值始终来自DWD，不再使用共享组快照数值覆盖它。Standard代表关系不适用于Oversize等其他类型。
6. 没有可用代表关系时，同值额度展示一份。存在差异时保留逐站明细，并按当前类别有效确定站点的最小剩余值进行保守预警估算，匹配依据明确标注此规则；不相加、不借其他店铺额度、不冒充平台已确认共享组。部分站点没有有效额度时，合计核查标记数据不足，不能宣称完整计划未超额。
7. 单位1为m³、2为ft³，统一乘`0.028316846592`转换。比较与同值判断使用Decimal原精度。额度“－”或未知单位不变成零、无限额度或真实超占用；合法零总额度允许展示。

## 本行与全量补货体积比较

单件体积优先读取最新`ods_datasync.lx_sales_mws_listing.dimension_info`包装长宽高，分别转换厘米/英寸；其次使用月仓储费长宽高/单件体积，最后用SKU包装尺寸。多仓、多站点取同对象最大单件体积，明确保留来源。缺值不当成0。实际商品类型来自中文库存表，体积并不从“仓储类型”字段推算。

Listing分批导入，必须按sid＋精确MSKU分别取最新记录（更新时间/创建时间及id排序），不能只取整表最后一个导入时间。该条件已加入回归验证，避免遗漏前面批次的商品。

- 本行体积＝页面及导出原有补货件数×单件m³。沿用现有MOQ、跟卖、ASIN合并和历史兜底后的显示数量，不使用另一个采购数量替换它。
- 店铺同类型合计＝同账号、国家类别、仓储类型下的全部正数显示补货需求体积之和。读取所选补货日期全量数据，不受页面分页、排序、分类周期、角色/国家/关键词筛选或导出范围影响。被合并后数量为0的来源不重复计入。
- 本行超出＝max(0，本行体积－有效剩余)；店铺合计超出＝max(0，合计体积－有效剩余)。使用Decimal原精度严格比较，“等于”不判超额。
- 计算含义为“假设本次原补货需求全部作为新增发货”的预警估算。剩余已经扣除在库与开放货件，不再减一次现有在途，也不把货件计划重新加到本次需求里。
- 部分正数需求缺类型或体积时，显示已知合计和缺项；已知合计已经超额仍预警，已知合计未超时不能宣称整组未超。不同国家类别、账号或类型不串组。
- 历史月份比较采用该月月底归档容量和当前可查类型/尺寸做估算，不能复原历史日真实发货状态。

| 状态 | 含义 |
|---|---|
| 本次补货未超库容 | 本行和完整店铺同类型合计均≤有效剩余；不是平台发货许可 |
| 本行补货超库容 | 本行体积＞剩余，列出本行超出量 |
| 本行未超，店铺合计超库容 | 本行未超但合计＞剩余，列出合计超出量；有缺项时注明为已知合计 |
| 本行未超，店铺合计数据不足 | 本行能计算，但其他需求缺类型、尺寸或额度，整组不能判未超 |
| 本行无需补货 | 原显示数量为0，新增体积为0；平台已有超占用/无剩余仍额外提示，不改数量 |
| 无法核算：具体缺项 | 真正缺类型、体积、有效额度、日期或关联时明确说明；不写“尚未判断”或笼统要求手动确认 |

“补货体积核查说明”列出本行和合计的计算结果、缺项及估算依据。正式接口已经完成类型匹配、单行体积、全量合计、剩余及超出计算，不再停留在只有来源额度的阶段。接口参数、数量和远端数据保存方式不变。

## 导出性能维护

2026-10-14排查发现，仓储费表约百万行且无MSKU查询索引，原每200个键分批查询反复扫描大表；匹配时每个商品又遍历整批仓储费、Listing、类型、包装及额度记录。修正为每请求按精确MSKU/SKU/sid建立索引，店铺关联只在该请求内复用，额度读取仍保留原始记录顺序。来源键按2000个分批，数量更大时继续分批，不无限扩大SQL参数。

Listing仍按sid＋二进制MSKU取最新有效记录，只读取本次对象所属店铺和国家类别的站点；先在小字段临时结果中选出id，再按主键取尺寸JSON，避免把大字段带进窗口排序。独立来源查询最多3路并行，各路使用独立连接，批次结果按原顺序合并；表头和月份等前置依赖先完成，不共享游标。Excel复用相同的对齐、字体和边框对象；保留所有字段、预警底色、跟卖边框和说明Sheet。没有增加跨请求缓存，没有更改库中索引、接口参数或补货数量。

性能验收使用隐藏后台的真实HTTP请求，日期2026-10-13，分别覆盖瘦狗30天469行和全部3700行；比较两份工作簿所有内部文件，除保存时间外必须完全一致，包含数值、标注、格式、边框和说明Sheet。取数/计算剖析日志与无剖析的实际HTTP耗时分开记录，不能把带剖析开销的时间当作用户等待时间。

本机实际HTTP单轮结果：全量3700行由72.915秒降至29.854秒；469行筛选导出由9.183秒变为10.085秒，未测得小份导出稳定提速。时间受远端查询和网络波动影响，不能承诺首次导出秒出。353项相关回归通过。大导出的改善主要来自消除逐对象全表扫描及减少重复数据库扫描；所有来源仍实时读取，补货数量、角色与显示规则不变。证据：[优化前计时](../../../outputs/export-http-before.json)、[最终计时](../../../outputs/export-http-after.json)、[工作簿一致性](../../../outputs/export-performance-integrity.json)。
