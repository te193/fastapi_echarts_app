# 补货追踪页面状态判断口径

本文档整理当前“补货追踪”页面已经使用的状态判断标准。口径来源于：

- `etl/replenishment_tracking_update.py`
- `app/services/replenishment_tracking_data.py`
- `app/static/js/replenishment_tracking.js`

## 1. 页面统计范围

补货追踪页只统计需要跟进的补货层级：

| 层级排序 | 层级 |
| --- | --- |
| 1 | 紧急补货 |
| 2 | 建议补货 |
| 3 | 计划补货 |

服务端固定过滤：

```sql
s.replenishment_level_sort in (1, 2, 3)
```

库存充足、日销为 0、历史兜底等层级不进入当前追踪页主统计。

## 2. 追踪窗口

页面支持的追踪窗口为 7 天、14 天、30 天。窗口从补货结果日期 `snapshot_date / cur_date` 开始，向后观察采购计划、FBA 计划、发货、收货状态。

判断窗口大致为：

```sql
>= 补货日期
< 补货日期 + tracking_window_days + 1 天
```

发货明细另有一个历史在途兜底：允许取补货日前 30 天内已发货、且预计/妥投日期覆盖到补货日之后的记录，用来识别“历史发货/历史在途”。

## 3. 主要数据来源

| 数据 | 当前来源表 |
| --- | --- |
| 补货结果、补货层级、补货数量、货值 | `dashboard_pur_plan_replenish_data` |
| 本地库存快照中的采购计划/采购在途 | `dashboard_restock_daily_snapshot` |
| 后续采购计划 | `dashboard_tracking_purchase_plan_sync`，来源于 `dwd_datasync.lx_purchase_purchase_plan` |
| FBA 发货计划 | `dashboard_tracking_fba_shipment_plan_sync`，来源于 `dwd_datasync.lx_fba_shipment_plan` |
| FBA 货件主表 | `dashboard_tracking_inbound_shipment_sync`，来源于 `dwd_datasync.lx_inbound_shipment_detail` |
| FBA 货件商品明细 | `dashboard_tracking_inbound_item_sync`，来源于 `dwd_datasync.lx_inbound_shipment_detail_ShangPinLieBiao` |

匹配粒度为：

```text
补货日期 + 国家类别 + 店铺 + MSKU
```

店铺会做简单标准化：如果源店铺名以 `-US`、`-UK` 等国家后缀结尾，会去掉最后 3 个字符后再匹配看板店铺。

## 4. 页面状态筛选标准

| 页面状态 | 判断条件 | 对应字段 |
| --- | --- | --- |
| 未建采购计划 | 追踪窗口内没有匹配到采购计划 | `purchase_planned_flag = 0` |
| 已建采购计划 | 追踪窗口内至少有 1 张采购计划 | `purchase_planned_flag = 1` |
| 已建本次 FBA | 本次采购链路内 FBA 计划数量大于 0 | `current_fba_shipment_plan_qty > 0` |
| 本次已发货 | 本次采购链路内实际发货数量大于 0 | `current_shipped_qty > 0` |
| 历史采购发货 | 历史链路实际发货数量大于 0 | `historical_shipped_qty > 0` |
| 已收货 | 本次链路收货数量大于 0 | `received_qty > 0` |

这些状态是筛选条件，不是互斥状态。一个 MSKU 可以同时满足“已建采购计划”“已建本次 FBA”“本次已发货”“已收货”。

## 5. 需要补货

“需要补货”不是在追踪页重新计算的，而是沿用补货结果表的层级判断。当前追踪页只看：

```sql
support_replenish_level_sort in (1, 2, 3)
```

对应：

- 紧急补货
- 建议补货
- 计划补货

补货建议数量使用：

```sql
replenish_qty
```

补货建议货值使用：

```sql
replenish_cost
```

## 6. 已采购 / 未采购

### 已建采购计划

追踪窗口内，存在采购计划即判定已建采购计划：

```sql
count(distinct pp.plan_sn) > 0
```

匹配条件：

- `pp.plan_create_time >= 补货日期`
- `pp.plan_create_time < 补货日期 + tracking_window_days + 1 天`
- `pp.country_category = 补货结果.country_category`
- `pp.seller_name_norm = 补货结果.seller_name_new`
- `pp.msku = 补货结果.seller_sku_adj`

### 未建采购计划

没有匹配到采购计划：

```sql
purchase_planned_flag = 0
```

### 采购数量

| 指标 | 判断 |
| --- | --- |
| 采购计划单数 | `count(distinct plan_sn)` |
| 采购计划总数 | `sum(quantity_plan)`，包含已完成和未完成采购计划 |
| 待采购计划数 | 仅统计 `status_text <> '已完成'` 的 `quantity_plan` |
| 最近预计到货 | 未完成采购计划中的 `expect_arrive_time` 最大值 |

如果本地快照里已经有采购在途数量，则页面把待采购计划数置为 0，避免已经转在途的采购计划继续显示为待采购：

```sql
case
    when purchase_shipping_quantity > 0 then 0
    else purchase_plan_qty
end
```

## 7. 本次采购在途 / 历史采购在途

采购在途来自本地快照的 `purchase_shipping_quantity`，再按追踪窗口内采购计划总数切分归因：

| 指标 | 判断 |
| --- | --- |
| 本次采购在途 | `least(purchase_shipping_quantity, purchase_plan_total_qty)` |
| 历史采购在途 | `greatest(purchase_shipping_quantity - purchase_plan_total_qty, 0)` |

也就是说，在途数量中能被窗口内采购计划数量覆盖的部分算“本次”，超出的部分算“历史”。

## 8. 已建 FBA 发货计划

### 本次 FBA

FBA 计划创建时间晚于或等于本 MSKU 最新采购计划创建时间，归为本次链路：

```sql
sp.plan_create_time >= latest_purchase_plan_time
```

本次 FBA 计划数量：

```sql
current_fba_shipment_plan_qty
```

页面“已建本次 FBA”筛选条件：

```sql
current_fba_shipment_plan_qty > 0
```

### 历史 FBA

没有本次采购计划，或 FBA 计划早于最新采购计划，归为历史链路：

```sql
latest_purchase_plan_time is null
or sp.plan_create_time < latest_purchase_plan_time
```

历史 FBA 计划数量：

```sql
historical_fba_shipment_plan_qty
```

## 9. 已发货

发货数量来自 FBA 货件商品明细：

```sql
quantity_shipped
```

### 本次已发货

货件关联的 FBA 计划时间，或货件时间，晚于等于最新采购计划时间：

```sql
coalesce(sp_link.plan_create_time, it.shipment_time, it.source_create_time) >= latest_purchase_plan_time
```

页面筛选条件：

```sql
current_shipped_qty > 0
```

### 历史采购发货

没有本次采购计划，或货件/FBA 计划时间早于最新采购计划时间：

```sql
latest_purchase_plan_time is null
or coalesce(sp_link.plan_create_time, it.shipment_time, it.source_create_time) < latest_purchase_plan_time
```

页面筛选条件：

```sql
historical_shipped_qty > 0
```

## 10. 已收货

收货数量优先取货件商品明细里的 `shipment_quantity_received`，没有则取 `quantity_receive`：

```sql
case
    when shipment_quantity_received > 0 then shipment_quantity_received
    else quantity_receive
end
```

页面“已收货”筛选条件：

```sql
received_qty > 0
```

当前列表里的 `received_qty` 是本次链路收货数量，取：

```sql
coalesce(current_received_qty, current_fba_plan_received_qty, 0)
```

## 11. 未发 / 未收

| 指标 | 判断 |
| --- | --- |
| 未发数量 | `max(本次 FBA 计划数量 - 本次已发数量, 0)` |
| 未收数量 | `max(本次已发数量 - 本次已收数量, 0)` |

对应字段：

```sql
pending_ship_qty
pending_receive_qty
```

## 12. 发货归因

字段：

```sql
shipment_attribution
```

判断标准：

| 值 | 判断 |
| --- | --- |
| `mixed` | 本次已发数量 > 0 且历史已发数量 > 0 |
| `current` | 本次已发数量 > 0，或本次 FBA 计划数量 > 0 |
| `historical` | 历史已发数量 > 0，或历史 FBA 计划数量 > 0 |
| `none` | 没有本次/历史 FBA 计划，也没有本次/历史发货 |

## 13. 最新状态文案优先级

列表中的 `latest_status` 按以下顺序取第一个命中的状态：

| 优先级 | 文案 | 判断 |
| --- | --- | --- |
| 1 | 本次链路已收货 | 本次收货数量 > 0 |
| 2 | 本次链路已发货 | 本次已发数量 > 0 |
| 3 | 已建本次 FBA | 已建采购计划，且本次 FBA 计划数量 > 0 |
| 4 | 已采购，存在历史发货 | 已建采购计划，且历史已发数量 > 0 |
| 5 | 历史采购发货 | 历史已发数量 > 0 |
| 6 | 历史 FBA 计划 | 历史 FBA 计划数量 > 0 |
| 7 | 本次+历史采购在途 | 本次采购在途 > 0 且历史采购在途 > 0 |
| 8 | 本次采购在途 | 本次采购在途 > 0 |
| 9 | 历史采购在途 | 历史采购在途 > 0 |
| 10 | 已建采购计划 | 采购计划单数 > 0 |
| 11 | 未进入采购链路 | 以上都不满足 |

## 14. 页面汇总指标

| 指标 | 判断 |
| --- | --- |
| 追踪 MSKU | 当前筛选范围内 `count(*)` |
| 已建采购计划 MSKU | `sum(purchase_planned_flag = 1)` |
| 未建采购计划 MSKU | `sum(purchase_planned_flag = 0)` |
| 采购计划单数 | `sum(purchase_plan_count)` |
| 采购计划总数 | `sum(purchase_plan_total_qty)` |
| 已建本次 FBA MSKU | `sum(current_fba_shipment_plan_qty > 0)` |
| 本次 FBA 计划数量 | `sum(current_fba_shipment_plan_qty)` |
| 本次已发 MSKU | `sum(current_shipped_qty > 0)` |
| 本次已发数量 | `sum(current_shipped_qty)` |
| 历史已发 MSKU | `sum(historical_shipped_qty > 0)` |
| 历史已发数量 | `sum(historical_shipped_qty)` |
| 已收货 MSKU | `sum(received_qty > 0)` |
| 已收货数量 | `sum(received_qty)` |
| 未发数量 | `sum(pending_ship_qty)` |
| 未收数量 | `sum(pending_receive_qty)` |

## 15. 注意事项

1. 状态筛选不是互斥枚举，而是按字段条件过滤。
2. “本次/历史”主要以最新采购计划时间为切分点。
3. 发货明细允许回看补货日前 30 天，用于识别补货日前已经在途、但仍影响当前补货判断的历史货件。
4. `latest_status` 是展示文案，有优先级；如果要做精确筛选，以第 4 节的状态字段为准。
5. 当前追踪页不重新计算补货层级和补货数量，只继承补货结果表。
