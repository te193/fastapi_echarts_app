# FBA 补货判定规则

## 1. 这套规则到底要解决什么

一个 MSKU 的库存分布在 FBA、本地仓和多批 FBA 在途货中。系统需要同时给出三件事：

```text
1. 要不要继续采购？
2. 现在到后面会不会断货？
3. 如果要补，走卡航、铁路还是海运？
```

原来的问题在于，所有状态库存直接相加后除以日销，得到一个总天数；例如显示 45 天，但当前 FBA 只能卖 20 天，下一批货 28 天后才可售，实际仍会断货。

新规则不再只看一个天数，而是分成两条线：

```text
总库存线：判断是否还要继续采购。
FBA 到货时间轴：判断什么时候会断货、已有补货是否足以覆盖、下一单该走什么物流。
```

---

## 2. 最终输出

每个 MSKU 最终输出以下五项，不再只输出“紧急补货/建议补货/计划补货”：

| 输出 | 含义 |
| --- | --- |
| 采购判断 | 需要采购 / 暂不采购 / 需要下一单 |
| FBA 风险 | 正常 / 安全库存预警 / 预计断货 |
| 已补货状态 | 无有效在途 / 已补货可覆盖 / 已补货但来不及 / 在途 ETA 缺失 |
| 物流建议 | 卡航 / 铁路 / 海运 / 不适用 |
| 判定原因 | 例如“第 2 批在途到货晚于安全边界” |

这样可以区分两种完全不同的情况：

```text
总货够，但 FBA 要断货：不一定继续采购，优先调拨或加急。
FBA 不会断货，但总货不够：需要采购，按时间轴选择合适物流。
```

---

## 3. 规则使用的字段

### 3.1 日销和库存字段

| 业务含义 | 字段 | 表 | 用途 |
| --- | --- | --- | --- |
| 预测日销 D | `pre_daily_avg_sales` | `dashboard_pur_plan_replenish_data` | 所有库存数量换算为天数 |
| FBA 当前严格可售数量 F | `afn_fulfillable_quantity` | 同上 | 时间轴的起点；当前真正可卖的库存 |
| FBA 在途总量 I | `stock_up_num` | 同上 | 总库存线使用 |
| 本地仓库存池 L | `local_quantity` | 同上 | 总库存线使用 |

本地仓库存已按业务口径定义为：

```text
local_quantity
= sc_quantity_local_valid
 + sc_quantity_purchase_shipping
 + sc_quantity_purchase_plan
 + sc_quantity_local_qc
```

规则中直接使用 `local_quantity`。四个组成字段只用于查看本地仓库存构成，不能再额外加一次。

### 3.2 为什么当前 FBA 可售不用 `available_total`

`available_total` 与 `afn_fulfillable_quantity` 在实际数据中存在差异，前者可能包含 FC 调拨预留、处理中或订单预留等数量。为了回答“现在真正还能卖几天”，第一版使用：

```text
当前 FBA 可售天数 A = afn_fulfillable_quantity / pre_daily_avg_sales
```

如果业务确认 `available_total` 才是当前可卖库存的权威口径，可以统一替换；但在规则未确认前，不应把它和严格 FBA 可售混为一谈。

## 4. 预计到货时间从哪里来

预计到货时间不是人工假设字段，当前系统已有完整来源链路。

### 4.1 字段来源链路

```text
dwd_datasync.lx_inbound_shipment_detail
    expected_arrival_date / eta_date / delivery_date
    shipment_sn / shipment_id
                │
                ▼
dashboard_tracking_inbound_shipment_sync
    expected_arrival_date / eta_date / delivery_date
    receiving_time / closed_time
                │  通过 shipment_sn 关联
                ▼
dashboard_tracking_inbound_item_sync
    msku / shipment_sn / quantity_shipped /
    shipment_quantity_received / quantity_receive
                │
                ▼
按 MSKU 聚合后的“FBA 在途批次时间轴”
```

具体来源如下：

| 时间或数量 | 同步后的字段 | 上游来源 | 说明 |
| --- | --- | --- |
| 预计到货日 | `expected_arrival_date` | `dwd_datasync.lx_inbound_shipment_detail.expected_arrival_date` | 第一优先级 ETA |
| ETA 备用日 | `eta_date` | `dwd_datasync.lx_inbound_shipment_detail.eta_date` | `expected_arrival_date` 为空时使用 |
| 送达日 | `delivery_date` | `dwd_datasync.lx_inbound_shipment_detail.delivery_date` | 当前不作为计划 ETA 主口径 |
| FBA 接收时间 | `receiving_time` | `dwd_datasync.lx_fba_shipment.receiving_time` | 已接收后的实际状态参考 |
| FBA 关闭时间 | `closed_time` | `dwd_datasync.lx_fba_shipment.closed_time` | 已完成后的实际状态参考 |
| 已发数量 | `quantity_shipped` | 入库货件商品明细 | 计算每批在途数量 |
| 已收数量 | `shipment_quantity_received`，备用 `quantity_receive` | 入库货件商品明细 | 从已发数量中扣除 |

现有同步逻辑中，货件表按 `shipment_id` 补充接收时间和关闭时间；货件商品明细再通过 `shipment_sn` 与货件表关联。因此，正式时间轴的批次粒度应是：

```text
站点 + 店铺 + MSKU + shipment_sn
```

### 4.2 预计到货不等于 FBA 可售

`expected_arrival_date` 表示预计到达时间，不表示已经可以在 FBA 销售。

因此，规则使用：

```text
预计 FBA 可售日期
= coalesce(expected_arrival_date, eta_date)
 + FBA 接收上架缓冲 H
```

示例：预计到货为 8 月 20 日，FBA 接收上架缓冲 `H = 7 天`，则这批货按 8 月 27 日变为可售计算。

如果 `expected_arrival_date` 和 `eta_date` 都为空，这批货仍可计入总库存，但不能放入时间轴，也不能用来停止断货预警。

如果“预计 FBA 可售日期”已经早于当前日期，但该批货仍存在未收数量，则将它标记为 `ETA 逾期`。这类货同样计入总库存，但不能假定它今天会自动变为可售，也不能触发已补货保护。

### 4.3 当前数据限制

目前 `receiving_time`、`closed_time` 的有效值很少，不能依赖它们预测未来可售时间；第一版必须用“预计到货日 + 缓冲 H”。

此外，现有追踪同步默认按发货时间取最近 30 天和未来窗口的数据。对于发货时间早于 30 天、但仍在途的海运货件，可能被漏掉。上线多批时间轴前，必须将取数范围调整为：

```text
状态未关闭
且 未收数量 > 0
且 预计到货日 >= 当前日期 - 容忍天数
```

而不是仅按发货日期限制 30 天。

## 5. 先算总库存：是否还要采购

总库存只回答“货量是否够”，不回答“今天会不会断货”。

```text
总库存数量 C
= FBA 当前严格可售 F
 + FBA 在途总量 I
 + 本地仓库存池 L

总库存可售天数 T = C / D
```

其中：

```text
F = afn_fulfillable_quantity
I = stock_up_num
L = local_quantity
D = pre_daily_avg_sales
```

设置一个总库存目标 `G`，初始建议为 90 天：

```text
T > G：暂不需要新采购。
T <= G：需要继续安排采购。
```

注意：`stock_up_num` 已经包含 FBA 在途总量。时间轴中会再次读取货件明细，但仅用于到货日期和批次顺序，不能把货件明细数量再次加到 `C`，否则会重复计算。

---

## 6. 再算 FBA 时间轴：什么时候会缺货

### 6.1 每一批有效 FBA 在途的定义

某 MSKU 的一批 FBA 在途货只有同时满足以下条件，才进入时间轴：

```text
quantity_shipped > quantity_received
expected_arrival_date 或 eta_date 有值
货件状态不是关闭、取消或异常
MSKU、站点、店铺能够和当前补货记录匹配
```

每批货先计算：

```text
未收数量 R = max(已发数量 - 已收数量, 0)
批次可售天数 Q = R / D
批次预计可售天数 E = 预计 FBA 可售日期 - 当前日期
```

其中已收数量按以下优先级获取：

```text
shipment_quantity_received
quantity_receive
0
```

同一 `shipment_sn`、同一 MSKU 的多行明细先汇总，再作为一批货处理，避免重复加入时间轴。

### 6.2 多批在途的时间轴算法

一个 MSKU 可以有多批在途，不能只看最近一批，也不能把全部在途数量直接相加。必须按预计可售日期从早到晚逐批模拟。

设：

```text
当前 FBA 可售天数 A = F / D
安全缓冲 B = 3 天（示例）
```

算法：

```text
coverage = A
last_day = 0
first_safety_day = 空
first_stockout_day = 空
按 E 从小到大遍历每一批货：
    coverage_before = coverage
    coverage = coverage_before - (E - last_day)

    如果 coverage < B：
        记录“该批到货前已触及安全边界”
        如果 first_safety_day 为空：
            first_safety_day = last_day + coverage_before - B
        如果 coverage < 0：
            同时记录实际断货天数
            如果 first_stockout_day 为空：
                first_stockout_day = last_day + coverage_before

    coverage = coverage + Q
    last_day = E

全部批次处理完成后：
    如果 first_safety_day 为空：
        first_safety_day = last_day + coverage - B
    如果 first_stockout_day 为空：
        first_stockout_day = last_day + coverage
```

含义：

- `first_safety_day`：不新增任何补货时，库存第一次在第几天触及安全库存。
- `first_stockout_day`：不新增任何补货时，库存第一次在第几天真正卖完。
- 任意一批到货前 `coverage < B`：即使最后总量很大，也说明中间存在安全库存预警。
- 任意一批到货前 `coverage < 0`：说明中间实际断货。

### 6.3 为什么必须这样算

假设：

```text
日销 D = 10
当前 FBA 可售 = 200 件，即 A = 20 天

第 1 批：10 天后可售，数量 100 件，即 Q = 10 天
第 2 批：35 天后可售，数量 300 件，即 Q = 30 天
```

时间轴：

```text
第 0 天：20 天库存
第 10 天，第 1 批到货前剩 10 天；加第 1 批后为 20 天
第 35 天，第 2 批到货前需要再消耗 25 天，库存变为 -5 天
```

结论：第 2 批到货前已经断货 5 天。虽然两批在途合计能支撑 40 天，也不能把它们直接加进当前库存后判断“不会断货”。

## 7. 已补货后，如何防止重复补货

“已补货保护”不是只要有在途单就生效，而是由时间轴结果决定。

### 7.1 可停止重复采购的条件

同时满足以下条件时，已有补货可以停止重复采购：

```text
1. 时间轴中至少有一批有效 FBA 在途。
2. 在任何一批到货前，库存都没有低于安全缓冲 B。
3. T > G，即总库存可售天数超过目标。
```

输出：

```text
采购判断：暂不采购
已补货状态：已补货可覆盖
FBA 风险：正常
```

即使当前 `A` 很小，只要第 1 批会在安全边界前可售，且后续批次也不会造成断档，系统就不应因为当前低库存而反复创建采购任务。

### 7.2 已补货及时到达，但仍要下一单

如果时间轴没有断档，但：

```text
T <= G
```

则已有货只解决当前和近期销售，总货量仍不足，应该创建下一单。

此时选择物流不能再看原始 `A`，而应看：

```text
first_safety_day
```

因为现有在途批次已经被放进时间轴，`first_safety_day` 才是真实的最晚安全补货时间。

### 7.3 已补货但仍会断货

如果任意一批货到货前库存已经低于 `B` 或小于 0：

```text
采购判断：根据 T 判断是否还需采购
已补货状态：已补货但来不及
FBA 风险：安全库存预警或预计断货
```

此时优先动作不是盲目重复采购，而是：

```text
本地仓立即建 FBA 计划并发货
加急已发 FBA 在途
同站点或跨站点调拨
必要时使用卡航或做断货预案
```

如果 `T > G`，总量已经足够，新采购通常不能解决最近断货问题；应输出“暂不重复采购，但需紧急保障 FBA 供给”。

### 7.4 有 FBA 在途数量但没有 ETA

若 `stock_up_num > 0`，但找不到某批货的 `expected_arrival_date` 和 `eta_date`：

```text
该数量计入 T。
该数量不计入时间轴。
该数量不触发已补货保护。
```

输出应明确标记：

```text
已补货状态：FBA 在途 ETA 缺失
运营动作：补充或核实 ETA
```

这比直接判“已补货、不再提醒”更安全。

## 8. 根据时间轴选择物流

物流时效必须是“从今天下单到 FBA 可售”的完整时效。

```text
LC = 卡航 25 天 + 接收上架缓冲 H
LR = 铁路 45 天 + 接收上架缓冲 H
LS = 海运 65 天 + 接收上架缓冲 H
```

示例：`H = 7 天` 时：

```text
LC = 32 天
LR = 52 天
LS = 72 天
```

如果需要继续采购，使用时间轴得到的 `first_safety_day` 选择最慢仍能赶上的物流：

| 条件 | 补货等级 | 物流建议 |
| --- | --- | --- |
| `first_safety_day < LC` | 极紧急 | 卡航也可能来不及；优先调拨、加急和断货预案 |
| `LC <= first_safety_day < LR` | 紧急补货 | 卡航 |
| `LR <= first_safety_day < LS` | 建议补货 | 铁路 |
| `first_safety_day >= LS` | 计划补货 | 海运 |

这是本规则最重要的变化：

```text
没有在途时：first_safety_day = A - B。
有一批或多批在途时：first_safety_day 必须由完整时间轴计算。
```

例如，当前只剩 20 天可售，但一批货 15 天后可售并能再支撑 40 天，则库存安全边界约在第 57 天。若今天需要下下一单，铁路 52 天能够赶上，海运 72 天赶不上。不能再因为当前 `A = 20` 而误判下一单必须卡航。

---

## 9. 最终执行顺序

```text
步骤 1：D <= 0？
        是：输出“日销为 0”，结束。

步骤 2：计算 A、T。

步骤 3：按 MSKU 找出全部有效 FBA 在途批次。
        每批计算未收数量、预计可售日期和 Q。

步骤 4：按预计可售日期运行多批时间轴。
        得到 first_safety_day、first_stockout_day、是否断档、是否缺 ETA。

步骤 5：T > G？
        是：暂不新增采购。
        否：需要采购或下一单。

步骤 6：时间轴是否断档？
        是：输出 FBA 风险和加急/调拨动作。
        否：已有补货可覆盖当前库存。

步骤 7：若需要采购，根据 first_safety_day 选择卡航、铁路或海运。
```

## 10. 示例

统一参数：

```text
D = 10 件/天
B = 3 天
H = 7 天
LC = 32 天
LR = 52 天
LS = 72 天
G = 90 天
```

### 示例 1：没有在途，当前库存不足，走卡航

```text
FBA 当前可售 F = 400 件，A = 40 天
FBA 在途 I = 0 件
本地仓库存池 L = 400 件
T = (400 + 0 + 400) / 10 = 80 天
```

没有在途时间轴：

```text
first_safety_day = A - B = 37 天
```

`T <= 90`，需要采购；`32 <= 37 < 52`，走卡航。

```text
采购判断：需要采购
补货等级：紧急补货
物流建议：卡航
```

### 示例 2：一批在途及时到达，不重复采购

```text
FBA 当前可售：200 件，A = 20 天
第 1 批：15 天后可售，未收 800 件，Q = 80 天
本地仓库存：0
T = (200 + 800) / 10 = 100 天
```

时间轴：

```text
第 15 天前，20 天库存剩 5 天
第 15 天加入 80 天库存，剩余 85 天
first_safety_day = 15 + 85 - 3 = 第 97 天
```

没有断档，且 `T > 90`。

```text
采购判断：暂不采购
已补货状态：已补货可覆盖
FBA 风险：正常
```

### 示例 3：一批在途解决当前问题，但下一单可走铁路

```text
FBA 当前可售：200 件，A = 20 天
第 1 批：15 天后可售，未收 400 件，Q = 40 天
T = 60 天
```

时间轴：

```text
第 15 天前剩 5 天
第 15 天加入 40 天，剩余 45 天
first_safety_day = 15 + 45 - 3 = 第 57 天
```

已有在途能防止当前断货，但 `T <= 90`，仍需安排下一单。铁路完整时效 52 天小于安全边界 57 天，因此铁路可以赶上。

```text
采购判断：需要下一单
已补货状态：已补货可覆盖
补货等级：建议补货
物流建议：铁路
```

### 示例 4：两批在途总量很多，中间仍断货

```text
FBA 当前可售：200 件，A = 20 天
第 1 批：10 天后可售，未收 100 件，Q = 10 天
第 2 批：35 天后可售，未收 300 件，Q = 30 天
```

时间轴：

```text
第 10 天前剩 10 天；加入第 1 批后为 20 天
第 35 天前还要消耗 25 天，库存变为 -5 天
```

```text
采购判断：根据 T 决定是否继续采购
已补货状态：已补货但来不及
FBA 风险：预计断货 5 天
运营动作：加急第 2 批、从本地仓调拨或使用卡航保障
```

### 示例 5：总库存足够，但 FBA 在途没有 ETA

```text
FBA 当前可售：200 件，A = 20 天
FBA 在途总量：800 件
本地仓库存池：100 件
T = 110 天
```

如果找不到这 800 件对应的有效 ETA：

```text
采购判断：暂不采购
已补货状态：FBA 在途 ETA 缺失
FBA 风险：无法确认是否会断货
运营动作：补录/核实货件 ETA；如当前库存不足则准备调拨或加急
```

## 11. 当前字段能否支持

### 可以直接支持

- 日销：`pre_daily_avg_sales`。
- 当前 FBA 可售：`afn_fulfillable_quantity`。
- 总 FBA 在途：`stock_up_num`。
- 本地仓库存池：`local_quantity`。
- 多批 FBA 在途的货件号、MSKU、已发、已收、预计到货：追踪入库货件和商品明细表。

### 必须补充为规则配置

```text
卡航、铁路、海运完整时效
FBA 接收上架缓冲 H
安全缓冲 B
总库存目标 G
物流渠道到卡航/铁路/海运的映射
```

### 上线前必须处理的字段限制

```text
1. 扩大未完成 FBA 在途货件的取数范围，不能只取最近 30 天发货记录。
2. expected_arrival_date 为空或 ETA 已逾期但仍未收货时，不能让该批货触发保护。
3. 同一 shipment_sn + MSKU 的多行必须先汇总，防止数量重复。
4. stock_up_num 只用于总库存，货件明细只用于时间轴，避免 FBA 在途重复加总。
```
