# 加权日销零持久化临时表实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 使用两张 MySQL 会话临时表加速加权日销，最终直接返回查询结果，不持久化任何过程表或结果表。

**Architecture:** 产品表现最近 30 天周期指标和 Listing 最新日售价分别写入 `CREATE TEMPORARY TABLE`。最终 CTE 直接读取两张临时表并 `SELECT` 输出，连接关闭后所有中间数据自动释放。

**Tech Stack:** MySQL 8、会话临时表、CTE、窗口函数、PyMySQL opt_db 集成测试、pytest。

## Global Constraints

- 产品表现只读取业务日期当天及此前 29 天。
- Listing 只读取最新同步日。
- 产品表现强制使用 `idx_osp_performance_dashboard_cover`。
- 不创建普通过程表、building 表或最终结果表。
- 连接关闭后数据库中不留下本任务表。
- 输出字段和全部业务公式与提交 `e51d345` 保持一致。

### Task 1: 删除最终持久化并恢复直接查询

**Files:**
- Modify: `data/补货页面加权日销计算.sql`

**Interfaces:**
- Consumes: 两张会话临时表、品牌和接收次数远端过程表。
- Produces: 19,059 行国家站点加权日销及广告预算结果集，不产生普通数据库表。

- [ ] **Step 1: 确认当前持久化行为为失败基线**

当前脚本在测试映射后执行并关闭连接，`information_schema.tables` 仍能查到：

```text

```

该行为不符合零持久化要求，是本次修复的红灯基线。

- [ ] **Step 2: 删除最终建表和换表语句**

从 SQL 中删除以下全部逻辑：

```text
DROP TABLE ... weighted_daily_sales_building
CREATE TABLE ... weighted_daily_sales_building AS
ALTER TABLE ... weighted_daily_sales_building ADD PRIMARY KEY
CREATE TABLE IF NOT EXISTS ... weighted_daily_sales LIKE ... building
DROP TABLE ... weighted_daily_sales_old
RENAME TABLE ...
```

- [ ] **Step 3: 将最终计算改为直接 SELECT**

保留原最终 CTE，将：

```sql
CREATE TABLE dws_datasync.dws_replenishment_weighted_daily_sales_building
ENGINE=InnoDB
DEFAULT CHARSET=utf8mb4
AS
WITH ...
SELECT ...;
```

改为：

```sql
WITH ...
SELECT ...
ORDER BY
    country_category,
    country,
    seller_name_new,
    seller_sku_adj;
```

输出继续包含 27 个字段，预算公式不变。

- [ ] **Step 4: 更新 SQL 文件头说明**

明确写明：

- 两张中间表都是 `CREATE TEMPORARY TABLE`；
- 最终结果直接查询返回；
- 当前连接关闭后不留下任何表。
