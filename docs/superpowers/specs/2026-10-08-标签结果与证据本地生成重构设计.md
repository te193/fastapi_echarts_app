# 标签结果与证据本地生成重构设计

状态：用户于 2026-10-08 确认开始后续实施；实施中，尚未切换或部署。

## 已确认的目标

用户要求先重构标签生成链路：标签结果和证据都在本地生成，停止使用远端已经计算好的标签结果和 evidence_json；完成后再修改业务规则。库存、销量、货件等业务源数据仍可从远端只读同步。

第一阶段基线为用户提供的 [原版 V47](../../../sqlcode/标签表数据插入_修改版_20260915_v47_产品表现前一日最大日期严格校验版.sql)，SHA256 为 `22e968cb5cba39eba83e2b56a0f3b1d60fa2a313c5976ac5c845e22be70e3055`。此前准备的“接收中归入断货中”修复版暂不部署，也不作为本次重构的规则基线。

## 现有链路已核实的事实

`etl/label_rule_evidence_snapshot_update.py` 的 `run_update` 从远端标签表获取最近两个标签日期，再复制标签事实和压缩后的 evidence_json 到本地 `dashboard_label_fact_snapshot.evidence_blob`。标签字典同步到 `dashboard_label_detail_snapshot`。

该模块已有本地销售角色核对表 `dashboard_label_rule_evidence_snapshot`，但它只是部分角色规则的核对，不是完整 V47 引擎。其版本标识仍为 `label_id_1_20260702_v1_raw_predict_profit`，不能当作用户提供的完整 V47 实现。

页面大部分标签统计和证据读取已经使用本地快照。页面手动刷新和每日任务均调用现有 `run_update`，因此可以通过替换生成端保留页面的读表接口。

本地数据库为 MySQL 8.0.46。现有 `dashboard_product_performance_daily` 是经过改名和聚合的看板数据，缺少 V47 使用的源记录 ID、源同步时间、产品创建时间、评价星级等完整字段，不能未经字段核对就替代原始产品表现表。

## 推荐方案及替代方案

推荐保留 SQL 计算引擎：将 V47 需要的业务源字段同步到专用本地源快照，再在本地 MySQL 执行受控映射后的 V47 过程。标签结果与 evidence_json 从同一轮计算产生，避免 Python 重写数千行规则造成阈值、日期、排序和 JSON 结构偏差。

Python 重写全部规则可获得更细的模块边界，但本次首轮迁移成本和口径漂移风险较大，暂不采用。直接在远端执行计算然后拉取结果不符合用户要求，也不采用。

主路径：远端业务源只读同步 → 完整本地输入批次 → 本地 V47 计算 → 标签与证据一致性验收 → 发布本地页面快照。

实现时逐表抽取 SQL 实际使用字段、类型、日期范围和索引，不盲目同步全表所有列。产品表现至少保留本规则使用的 2026 年历史；货件不能只同步最近 30 天，否则首次到货和历史货件数会变化。保留规则原有商品粒度及源记录排序字段。

标签详情是规则元数据，可以同步字典，但计算过程只读取已经保存的本地字典；字典版本及哈希纳入批次。不得从远端标签事实或 evidence_json 取值、补齐、兜底或作为历史种子。

## 计算与发布边界

1. 建立专用 `dashboard_label_source_*` 输入表、计算工作表、本地执行日志和批次状态。所有建表、写入和过程调用仅使用本地连接；源连接只允许 select、show 等读取。
2. V47 中源表名通过显式映射替换到本地输入表；远端标签表引用全部映射为本地产生的计算工作表，过程名和日志表也本地化。不使用字符串全局替换 schema 的方式误改无关内容。
3. 执行前检查所有 SQL 表引用都在本地白名单中，禁止远端过程调用、事件创建和未映射的标签表读取。Python 执行过程定义时处理 MySQL 客户端 delimiter 指令，不把它当作服务器语句发送。
4. 所有规则、标签 ID、统计窗口、字段和 evidence_json 合同保持原版 V47。自动运行仍要求产品表现最大业务日期等于客户端业务时区的前一日，手动补算日期必须存在源数据。
5. 原版过程内部多次提交，不能在页面正式表上直接执行。先在计算工作表生成完整日期，再检查业务键、标签字典引用、证据字段、重复命中和源批次，最后原子更新供页面读取的标签事实与证据快照。
6. 输入不完整、计算失败或验收失败时，页面继续显示上一次成功批次，并返回本次失败原因。不得把半轮结果发布，也不得悄悄改回读取远端成品标签。
7. 发布后统一失效标签看板、国家标签看板和详情缓存。手动刷新和每日任务使用同一个入口，报告 business_date、input_batch、rule_version、input_hash、fact_rows、evidence_rows、耗时和失败阶段。

## 历史状态初始化必须明确

V47 并非纯当天函数：成熟期会沿用历史首次成熟日期；断货前标签 20/21 沿用上一日同一轮次已生成的角色和证据；标签 23 沿用上一日连续出现次数。因此不能只计算当天、再把旧远端证据当种子。

本地结果历史须独立保存，页面可以仍只展示最近两期。首次建立本地链路时，对具有完整业务源历史的日期按日串行回算，再计算目标日期；必须记录最早可可靠回算日期和历史覆盖完整性。

标签 23 的旧累计起点为 2026-09-03；如果无法完整回算对应时期，不得将从本地首跑开始的次数声称为原累计次数。成熟期和断货前事件也不能用当前源表伪造历史时点状态。对无法还原的历史明确给出依据不足及覆盖范围，提交具体差异后再决定切换条件。

保留原版 V47 的货件时间口径，不在本次迁移偷偷补日期截止或货件有效期规则。当前源表不代表不可变历史快照，回算结果的时间语义必须说明。

## 验收

所有测试与实跑均以隐藏窗口后台执行，输出日志和退出状态。

需要验证：纯本地计算过程只引用白名单；源端无写入且不读取远端成品标签；日期校验、空源、重复重跑、同日失败恢复及历史串行续接；各父子标签粒度及字典覆盖；证据和标签结果同批产生；页面仍能统计和下钻；生成失败时旧批次完好。

V47 的关键边界样例应覆盖角色阈值、零销量／零库存、退货、待上架、清仓、返场、断货前沿用、站点策略及连续次数。对本地生成的实际批次逐项核对源证据与命中规则，不以“非空”或总数相等代替验证。

本次重构保持旧 V47 的接收中覆盖缺口，以便迁移与业务修复分开验收；本地链路通过后再应用用户已确认的“接收中归入断货中”改动。

## 成本与切换条件

首次同步和历史回算可能显著增加网络传输、本地磁盘占用和计算耗时；实际预算需以逐表字段量、日期覆盖及一个完整本地批次的实测为准，当前不承诺耗时。

只有本地输入完整、计算及发布测试通过、历史覆盖差异清楚、页面实测正确后，才切换正式入口。禁止为了完成切换而复制远端标签和旧证据。本设计审核后再形成实现计划与执行顺序。
