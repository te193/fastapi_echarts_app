# 补货页面合并库存支撑天数显示设计

## 结论

补货明细的“库存 / 交期”列统一采用与交期弹窗相同的数据范围。对于同 ASIN 合并补货的主链接，黑体当前支撑天数显示同 ASIN 合并库存的支撑天数；普通商品继续显示自身库存支撑天数。

本次只调整页面接口的显示值及该列排序，不修改 ETL、数据库原始字段、补货数量、补货层级、导出或其他页面。

## 当前问题

同 ASIN 主链接目前混用了两种范围：

- 黑体“当前支撑天数”读取单个 MSKU 的 `inventory_support_days`。
- 弹窗“到货时支撑”读取同 ASIN 合并后的 `arrival_inventory_support_days`。

例如黑体显示 23.39 天，采购交期 20 天，弹窗到货时支撑显示 45.95 天。两个数字无法直接相减，是因为前者是单链接库存，后者是同 ASIN 合并库存。

## 设计

在补货明细接口查询中生成页面专用的当前支撑天数：

```text
页面当前支撑天数 = 到货时支撑天数 + 有效采购交期天数
```

同 ASIN 主链接的到货时支撑和交期已经使用合并口径，因此可以还原合并后的当前支撑天数。以上例计算：`45.95 + 20 = 65.95 天`。

普通商品满足“到货时支撑 = 当前支撑 - 交期”，因此按同一公式计算后仍为原来的自身支撑天数，不改变普通商品显示。

当到货时支撑或采购交期缺失时，回退到数据库已有的 `inventory_support_days`，避免历史快照或不完整数据变为空值。

## 数据流

1. 数据库继续保留原有 `inventory_support_days` 和到货相关字段。
2. 补货明细查询使用一个显示表达式，将计算结果别名为 `inventory_support_days`。
3. API 序列化继续输出现有 `support_days`，前端无需增加字段或列。
4. “库存 / 交期”列排序使用相同显示表达式，保证显示值与排序口径一致。

## 明确不变的范围

- 不重新运行或修改补货 ETL。
- 不覆盖数据库中的 `inventory_support_days`。
- 不修改补货层级及层级排序。
- 不修改补货需求量、最终补货量、箱数或成本。
- 不修改导出字段和导出口径。
- 不修改同 ASIN 合并分配规则。

## 测试与验收

- 接口 SQL 对页面支撑天数使用“到货时支撑 + 交期”的显示表达式。
- `support_days` 排序使用同一个表达式。
- 任一组成字段缺失时回退原库存支撑天数。
- 序列化和前端仍使用现有 `support_days` 字段。
- 相关单元测试和完整测试通过。
- 8002 测试服务重启后，可在同 ASIN 主链接上看到黑体值与弹窗满足“当前支撑 - 交期 = 到货时支撑”。
