# 加权日销 DWS 分层性能优化设计

## 目标

将现有一次性 CTE 查询改为“会话临时表 + DWS 最终表”分层脚本，减少重复扫描、排序和聚合，缩短加权日销及广告预算的全量计算时间。最终指标口径、国家站点粒度和输出字段保持不变。

## 已确认的性能瓶颈

- `dwd_datasync.lx_statistics_product_performance` 约 470 万行，最近 30 天约 56.9 万行。
- 当前查询通过动态 CTE 生成日期边界，执行计划对产品表现主表选择 `ALL` 全表扫描。
- 同口径 30 天日聚合实测：普通扫描约 11.8 秒；强制使用 `idx_osp_performance_dashboard_cover` 后约 5.0 秒。
- Listing 当前约 5.8 万行，原查询对全部有效数据执行 `ROW_NUMBER()` 和 `Using filesort`；业务只需要最新同步日。

## 方案选择

采用两张 MySQL 会话临时表和一张 DWS 正式表：产品表现 30 天周期汇总、Listing 最新日售价、最终加权日销结果。

未采用以下方案：

- 每个原 CTE 都拆成过程表：表数量和索引维护成本过高。
- 只创建一张最终结果表：仍需在单个语句中完成大表扫描、窗口排序和多次聚合，性能收益有限。

## Schema 映射

| 用途 | Schema | 表名前缀 |
| --- | --- | --- |
| 测试临时表与结果表 | `opt_db` | `tmp_` |
| 正式会话临时表 | `dws_datasync` | `tmp_` |
| 正式结果表 | `dws_datasync` | `dws_` |

正式脚本最终使用 `dws_datasync`。测试执行时将两个临时表和一个正式结果表映射到对应 `opt_db.tmp_` 表，业务 SQL 不改变。两个中间表使用 `CREATE TEMPORARY TABLE`，数据库连接关闭后自动释放。

## 业务日期

业务日期使用：

```sql
SET @biz_date = (
    SELECT DATE(MAX(start_date))
    FROM dwd_datasync.lx_statistics_product_performance
);
SET @product_start_date = DATE_SUB(@biz_date, INTERVAL 29 DAY);
SET @product_end_date = DATE_ADD(@biz_date, INTERVAL 1 DAY);
```

使用 `DATE(MAX(start_date))`，不再使用 `MAX(DATE(start_date))`，以便 MySQL 利用 `start_date` 索引末端取得最新值。

Listing 日期独立取最新同步日：

```sql
SET @listing_date = (
    SELECT DATE(MAX(create_time))
    FROM dwd_datasync.lx_sales_mws_listing
);
SET @listing_end_date = DATE_ADD(@listing_date, INTERVAL 1 DAY);
```

## 表一：产品表现最近 30 天周期汇总临时表

正式表名：

```text
dws_datasync.tmp_replenishment_weighted_sales_product_30d
```

职责：

- 只读取 `@product_start_date <= start_date < @product_end_date`；
- 使用 `FORCE INDEX (idx_osp_performance_dashboard_cover)`；
- 统一国家类别、店铺名和 MSKU；
- 内层先聚合到 `dt_date + country_category + country + seller_name_new + seller_sku_adj`，保证同一天只计算一个可售日；
- 外层直接落成每个国家、店铺、MSKU 的 3/7/14/30 天销量和可售天数；
- 只生成约 1.9 万行周期指标，不把约 56.9 万行日明细写入中间表，也不建立一次性宽索引。

该表只保留滚动 30 天，不保存更早产品表现。当前最长计算周期为 30 天，因此不会损失任何周期销量、可售天数或加权日销信息。

## 表二：Listing 最新日售价临时表

正式表名：

```text
dws_datasync.tmp_replenishment_listing_price_latest
```

职责：

- 只读取 `@listing_date <= create_time < @listing_end_date`；
- 排除空值和非正数 `landed_price`；
- 在最新同步日内按国家、店铺、MSKU 取 `create_time` 最新的有效记录；
- 关联 Listing 同步月份的 `dwd_datasync.lx_basic_currency.rate_org`；
- 保存原币售价、币种代码、官方汇率及人民币售价。

主键：

```text
(country_category, country, seller_name_new, seller_sku_adj)
```

Listing 只保留最新同步日，不再对历史日期执行窗口排序。SEK 继续映射到汇率表的“瑞典”。

## 表三：最终加权日销结果

正式表名：

```text
dws_datasync.dws_replenishment_weighted_daily_sales
```

职责：

- 直接读取产品表现 30 天周期临时表中的 3/7/14/30 天销量和可售天数；
- 保持现有周期日销平滑逻辑；
- 品牌、接收次数和新品/老品继续从原远端过程表计算；
- 新品/老品保持国家类别维度并下发到国家明细；
- 连接 Listing 最新日售价，计算原币和人民币广告预算；
- 输出字段和精度与当前 SQL 一致。

主键：

```text
(biz_date, country_category, country, seller_name_new, seller_sku_adj)
```

广告预算公式保持：

```text
ad_budget_original = listing_price × 5% × daily_avg_sales × 30
ad_budget_cny      = listing_price × exchange_rate_cny × 5% × daily_avg_sales × 30
```

## 临时表释放与原子换表

两个中间表每次在同一数据库连接中创建，分别只扫描 30 天和 1 天数据。它们使用 `CREATE TEMPORARY TABLE`，连接关闭后由 MySQL 自动释放，不需要人工清表。

最终结果先构建：

```text
dws_datasync.dws_replenishment_weighted_daily_sales_building
```

全部数据和索引完成后，通过 `RENAME TABLE` 将 `_building` 与正式表原子切换，再删除旧表。下游不会读取到部分写入或空结果。

建表脚本在开始时删除上次异常遗留的最终 `_building` 表。不会留下普通中间表，也不会删除或修改五张远端源表。

## 失败处理

- 产品临时表构建失败：停止执行，连接关闭后自动释放临时表，保留上一版最终结果表。
- Listing 临时表构建失败：停止执行，连接关闭后自动释放临时表，保留上一版最终结果表。
- 最终 `_building` 构建失败：正式结果表不切换；下次运行开始时删除遗留的构建表后重建。
- 仅汇率缺失时，原币预算正常返回，人民币预算保持 `NULL`。

## 验证标准

1. 产品表现源查询边界固定为 `biz_date - 29 天` 至 `biz_date`，周期临时表与旧口径的销量和可售天数一致。
2. Listing 临时表全部来自 `MAX(DATE(create_time))`，每个国家、店铺、MSKU 只有一行。
3. 最终表的销量、可售天数、周期日销、加权日销和广告预算与改造前 SQL 完全一致。
4. EUR、PLN、SEK、GBP、USD、CAD、TRY、MXN、BRL 均能正确关联汇率。
5. 产品表现扫描使用 `idx_osp_performance_dashboard_cover`，不再由优化器选择 470 万行全表扫描。
6. 记录端到端构建耗时，并与改造前实测约 28.3 秒的基线比较；opt_db 实测刷新约 16.7 秒。
7. 项目完整回归测试通过。
