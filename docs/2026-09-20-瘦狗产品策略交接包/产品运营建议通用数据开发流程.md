# 产品运营建议通用数据开发流程

## 1. 用途、边界与交接方式

本文定义一套可复用的“产品运营建议”数据开发契约。它承载任意销售角色的产品级价格/成本结论和广告原子动作，不把瘦狗、问题产品、潜力产品或未来角色写死在表名、主键或公共字段中。

后续接入一个新销售角色时，开发人员只需拿到：

1. 本文；
2. 该角色的运营规则文档；
3. 第 7 节规定的策略输入清单；
4. 历史策略表的数据连接与字段映射。

无需另建同构结果表，也不需要改写通用历史策略状态核验、数据质量、输出、幂等和验收逻辑。

本期文档不执行任何 `create`、写入、审核回写或平台操作。结果表是**待审核建议快照**，不是审核流、执行流水、价格写入或广告 API 队列；实际完成状态只从既有策略审核系统读取。

## 2. 通用架构

```mermaid
flowchart lr
    a[角色规则文档] --> b[策略适配层]
    r[新策略规则配置表] --> b
    c[标签、经营、成本、定价、库存、广告、预算快照] --> d[统一指标层]
    e[历史策略批次与策略项] --> f[历史策略状态核验]
    d --> f
    b --> g[角色路径与动作规则]
    f --> g
    g --> h[产品级价格/成本决策表]
    g --> i[广告原子动作表]
    h --> j[人工审核/既有策略系统]
    i --> j
    j -.下一运行日只读历史状态.-> f
```

固定顺序如下，所有销售角色均须遵守：

```text
源数据可用性与既定快照节奏校验
→ 历史策略状态核验
→ 角色样本准入
→ 角色路径判定
→ 价格/成本判断
→ 广告状态与对象规则
→ 库存、预算与动作上限
→ 两张结果表幂等输出
```

前序拦截优先于后序规则。若历史、库存或映射不可用，不能为了产生“看起来完整”的建议而填充数值动作；应输出明确的待核或拦截状态。降 bid、否词、暂停、预算回收等风险收缩动作是否可以越过拦截，必须由角色规则显式说明。

`data_date` 固定为运行日 `D`，而不是要求每张来源表同一天：标签和广告表现允许且应当取 `D-1` 的最新完整快照；价格、成本、库存、预算及其他经营事实取 `D` 的最新快照。运行时必须将每个来源的实际日期写入证据。只有来源未满足这个既定节奏、超过允许滞后，或角色规则未配置滞后口径时，才标记 `source_date_mismatch`。

### 2.1 新策略规则配置表

现有 `dws_datasync.dws_产品策略建议表` 只作为字段形态参考，**不直接使用，也不改造**。新流程应独立新建一张通用规则配置表：

`dws_datasync.dws_product_strategy_rule_config`

它是规则文档被拆解后的结构化动作目录；两张每日结果表则记录“今天哪个产品或广告对象命中了哪条业务动作”。一条配置记录必须对应一个可独立审核的价格、成本结论或广告原子动作，不能把多个条件分支、多个动作拼在同一条规则里。样本准入、数据质量、历史执行状态、库存、预算、动作上限与复盘属于运行引擎控制，不进入本表。

| 字段 | 建议类型 | 用途 |
|---|---|---|
| `strategy_rule_id` | `bigint` | 规则配置表主键。 |
| `rule_code` | `int` | 六位数字规则码，唯一且写入两张每日结果表。 |
| `problem_type` | `varchar(100)` | 面向业务展示的策略类别，例如“瘦狗产品-广告调整”。 |
| `hit_condition` | `text` | 该业务动作自身的触发条件，写清指标、比较符、阈值和周期；不写样本准入、数据/历史、库存、预算或动作上限。 |
| `tag_name` | `varchar(255)` | 面向业务展示的规则名称或标签名称。 |
| `strategy_action` | `text` | 明确动作、幅度、目标值或停止条件。 |
| `target_price` | `varchar(100)` | 兼容现有业务表字段形态；可填价格线、`CURRENT_PRICE`、`NO_PRICE_CHANGE` 或其他动作目标。 |
| `observation_period` | `varchar(500)` | D+3、D+7、D+14、成熟 30 天等复盘方式与周期。 |
| `strategy_scope` | `varchar(64)` | 销售角色策略域，例如问题、瘦狗、潜力等；不在物理表名中写死。 |
| `rule_version` | `varchar(64)` | 规则版本。 |
| `decision_domain` | `varchar(32)` | 价格、成本或广告。 |
| `action_type` | `varchar(64)` | 产品价格/成本结论或广告原子动作类型。 |
| `threshold_definition` | `json` | 仅保存动作幅度、价格档位、对象门槛等动态参数，使用简短 JSON；不得重复 `hit_condition`、`action_type` 等稳定字段。 |
| `is_enabled` | `tinyint` | 启停标记。 |
| `effective_start_date` | `date` | 生效起始日期。 |
| `effective_end_date` | `date` | 生效结束日期。 |
| `source_document` | `varchar(255)` | 规则来源文档。 |
| `source_section` | `varchar(255)` | 规则来源章节。 |
| `created_time` | `datetime` | 规则建档时间。 |
| `updated_time` | `datetime` | 规则变更审计时间。 |

运行引擎根据 `decision_domain + action_type` 推导同类历史匹配、正向/止损属性与互斥处理；样本、日期、数据、历史、库存、预算和动作上限的检查结果只进入运行日志及每日结果 `evidence_json`，不回写为规则配置记录。

前八列保留现有策略表的业务可读形态，便于运营审核；后十七列提供跨角色开发、版本、阈值、互斥和状态核验所需的稳定控制字段。建议以 `strategy_rule_id` 为主键，并对 `rule_code + rule_version` 建唯一约束；同一规则码在同一版本只能有一条有效定义。`threshold_definition` 与每日结果表的 `evidence_json` 不同：前者只保存简短的规则参数，例如 `{"params":"orders=0；15<=clicks<=24；bid_change=-12%"}`；后者保存某次运行的实际指标和证据。规则文档没有给出精确参数时，新 Codex 必须标为待确认，不得填入猜测阈值。

规则码固定为六位：`RDAAVV`。

| 位段 | 含义 | 规则 |
|---|---|---|
| `R`（第 1 位） | 销售角色 | `1` 问题产品，`2` 瘦狗产品，`3` 潜力产品，`4–8` 预留给后续角色。 |
| `D`（第 2 位） | 决策域 | `1` 价格，`2` 成本，`3` 广告；`4–9` 预留。样本、路径、数据、历史、库存、预算、动作上限和复盘不单独占规则码，它们是命中动作前后的引擎级检查。 |
| `AA`（第 3–4 位） | 动作族 | 同一类动作使用同一动作族编码。 |
| `VV`（第 5–6 位） | 条件变体 | 具体阈值、分支或动作幅度的变体，`00–99` 预留。 |

例如 `110100` 表示“问题产品 / 价格域 / 动作族 01 / 变体 00”；对应瘦狗的同类动作只改首位为 `210100`。首位只能表达角色，后五位必须保持规则域和动作含义稳定；阈值可以随角色不同，但必须分别写入各自的 `hit_condition`、`threshold_definition` 和 `strategy_action`。

新 Codex 接入一个角色规则文档时，必须按以下方式拆解并建档：

1. 先按路径、价格、成本、广告和数据/历史状态拆成原子规则；一个可独立输出的动作或结论对应一行。库存和预算只写成正向动作的执行条件，不拆成独立标签或规则行。
2. 从原文逐项抽取样本条件、指标窗口、比较符、具体阈值、P 线、bid/预算幅度、动作上限、互斥关系、缺失处理和复盘期；不得只写“按策略调整”。
3. 按 `RDAAVV` 分配规则码，并在规则文档中回填该编码；同类角色动作复用后五位，只改首位。
4. 将规则码、规则版本和 `strategy_rule_id` 绑定到每日候选输出；未建档或映射不唯一的候选只能输出 `data_pending`。
5. 用验收样例逐条验证命中、不命中、边界、历史阻断和动作互斥，确认后才启用 `is_enabled=1`。

## 3. 通用结果表结构

### 3.1 表一：产品级价格/成本决策

表名：`dws_datasync.dws_product_price_cost_decision_daily`

粒度：`data_date + strategy_scope + rule_version + country + store + msku`。

| 字段 | 建议类型 | 通用含义 |
|---|---|---|
| `data_date` | `date` | 本次运行日 `D`；各来源实际快照日按既定 D/D-1 节奏记录在证据中。 |
| `country_category` | `varchar(20)` | 国家类别。 |
| `country` | `varchar(100)` | 国家/站点。 |
| `store` | `varchar(255)` | 店铺。 |
| `msku` | `varchar(500)` | 产品 MSKU。 |
| `asin` | `varchar(100)` | 产品 ASIN；无法唯一时允许为空，但需标记映射异常。 |
| `product_name` | `varchar(500)` | 产品名快照。 |
| `strategy_scope` | `varchar(64)` | 可配置策略域标识，用于区分不同销售角色；不预设枚举。 |
| `strategy_rule_id` | `bigint` | 逻辑关联 `dws_product_strategy_rule_config.strategy_rule_id` 的规则配置标识。 |
| `rule_code` | `int` | 本条结论的数字规则编码，作为规则目录快照冗余保存。 |
| `strategy_period` | `varchar(20)` | 该规则使用的指标观察期，例如 `30d`、`7d` 或 `current`。 |
| `decision_type` | `varchar(64)` | 产品级决策类型，由策略输入定义。 |
| `current_price` | `decimal(20,6)` | 当前售价；非价格策略可为空。 |
| `suggested_price` | `decimal(20,6)` | 建议售价；没有调价时必须为空，不能以当前价代替。 |
| `price_direction` | `varchar(16)` | `increase`、`decrease`、`hold`、`none`。 |
| `cost_diagnosis_required` | `tinyint` | 是否需要成本归因诊断。 |
| `history_strategy_status` | `varchar(64)` | 历史策略状态核验结论。 |
| `history_review_id` | `bigint` | 已关联的历史策略批次 `amazon_strategy_review.id`。 |
| `history_review_item_id` | `bigint` | 已关联的历史策略明细 `amazon_strategy_review_item.id`。 |
| `history_task_item_id` | `bigint` | 历史任务 SKU 快照 ID，即明细表的 `task_item_id`；用于追溯原任务。 |
| `history_batch_status` | `varchar(30)` | 历史批次的物理 `status` 快照；是当前执行/观察状态的唯一直接来源。 |
| `history_item_outcome` | `varchar(30)` | 历史明细的物理 `outcome` 快照；仅表达该 SKU 的复盘结果，不冒充执行状态。 |
| `history_status_time` | `datetime` | 历史批次 `update_time` 快照；不等同于单 SKU 的实际执行完成时间。 |
| `next_review_date` | `date` | 下一 D+N 或成熟期复盘日。 |
| `data_status` | `varchar(64)` | 数据质量和映射状态。 |
| `rule_version` | `varchar(64)` | 规则版本。 |
| `created_time` | `datetime` | 本次建议生成时间。 |
| `updated_time` | `datetime` | 同日重跑更新时间。 |
| `evidence_json` | `json` | 业务证据容器；不固定结构。 |

建议主键与索引：

```sql
primary key (data_date, strategy_scope, rule_version, country, store, msku)
index idx_product_decision_status (data_date, data_status, history_strategy_status)
index idx_product_decision_rule (data_date, strategy_scope, rule_code)
```

### 3.2 表二：广告原子动作

表名：`dws_datasync.dws_product_ad_action_daily`

粒度：`data_date + strategy_scope + rule_version + action_key`。一行只表达一个可以独立审核的广告原子动作。

| 字段 | 建议类型 | 通用含义 |
|---|---|---|
| `data_date` 至 `product_name` | 与产品表一致 | 用于产品级关联与筛选。 |
| `strategy_scope`、`strategy_period` | `varchar` | 与产品表一致，标识角色规则来源。 |
| `strategy_rule_id` | `bigint` | 与产品表一致，关联新规则配置表主键。 |
| `rule_code` | `int` | 与产品表一致，保存六位数字规则码。 |
| `action_key` | `char(64)` | 稳定、可重算的广告动作唯一键。 |
| `action_type` | `varchar(64)` | 广告动作类型，由策略输入定义。 |
| `profile_id` | `varchar(128)` | 广告账户/档案标识。 |
| `campaign_id`、`ad_group_id` | `varchar(128)` | 活动和广告组标识。 |
| `ad_entity_type`、`ad_entity_id` | `varchar(64)`、`varchar(128)` | 可执行广告实体类型及标识。 |
| `object_type`、`object_id` | `varchar(64)`、`varchar(256)` | 关键词、商品投放、自动对象等。 |
| `search_term` | `varchar(500)` | 否词或加词场景的规范化搜索词/ASIN。 |
| `current_value`、`suggested_value` | `decimal(20,6)` | 当前和建议 bid、预算等数值；非数值动作为空。 |
| `suggested_text` | `varchar(500)` | 否词文本、建议关键词等非数值动作内容。 |
| `change_rate` | `decimal(12,6)` | 相对改变量，例如 `0.08` 表示 `+8%`。 |
| `cost_diagnosis_required` | `tinyint` | 产品需成本诊断时同步给广告审核侧。 |
| `history_strategy_status` 至 `next_review_date` | 与产品表一致 | 广告实体/对象级的历史策略状态核验信息。 |
| `data_status`、`rule_version`、`created_time`、`updated_time`、`evidence_json` | 与产品表一致 | 质量、版本、时间和弹性证据。 |

建议主键与索引：

```sql
primary key (data_date, strategy_scope, rule_version, action_key)
index idx_product_ad_action_product (data_date, strategy_scope, country, store, msku)
index idx_product_ad_action_status (data_date, data_status, history_strategy_status)
index idx_product_ad_action_entity (profile_id, campaign_id, ad_group_id, ad_entity_id)
```

### 3.3 `evidence_json` 的边界

`evidence_json` 仅要求写入合法 JSON，不制定统一 schema，不要求固定键名，也不以 JSON 内键名作为下游执行的唯一条件。开发按规则场景保存足以复核的命中指标、来源快照、阈值、计算证据和拦截原因即可。

产品和广告审核、幂等、历史关联、执行定位所需的信息必须在独立字段中存在，不能只存在于 JSON。这样未来新增销售角色或动作类型时只需扩展规则与证据，而不必频繁改表。

## 5. 已核实上游表字段字典

本节字段来自 2026-09-20 对当前 `opt_lyt` 只读连接的 `information_schema.columns` 核验。它说明“当前可直接使用什么”，不等同于永久 API 契约；开发上线时仍需做字段存在性和快照新鲜度检查。

### 5.1 标签来源

来源：`dws_datasync.dws_标签表汇总`

| 物理字段 | 用途 |
|---|---|
| `data_date` | 标签业务日期。 |
| `country_category`、`country` | 国家类别和国家。 |
| `store`、`msku` | 标签关联键。 |
| `label_id`、`label_period` | 角色样本的标签和周期条件。 |
| `created_time`、`evidence_json` | 标签生成时间与标签证据。 |

角色规则必须自行说明其标签条件和关联键。例如某标签可能只有店铺 + MSKU 粒度、国家为空；开发不能默认所有标签都可以按 `country + store + msku` 关联。

### 5.2 经营与八项成本来源

来源：`temporary_dwd.产品近30天八项成本_每日快照_v4`

推荐使用字段：

| 字段 | 用途 |
|---|---|
| `数据日期`、`统计窗口开始日期`、`统计窗口结束日期`、`销售数据截止日期` | 统一快照日、实际窗口天数和数据截止日检查。 |
| `国家`、`店铺名`、`msku`、`asin`、`品名` | 产品身份关联。 |
| `近30天销量`、`近30天订单数`、`近30天净销售额_cny` | 日销、订单和分母口径。 |

| `采购成本_cny`、`头程成本_cny`、`FBA费用_cny`、`佣金成本_cny`、`税费成本_cny`、`广告成本_cny`、`退款成本_cny`、`仓储及其他调整_cny` | 八项成本诊断。 |

#### 5.8.3 历史适配输出与限制

历史适配层至少输出 `review_id`、`review_item_id`、`task_item_id`、`batch_status`、`item_outcome`、`batch_status_time`、产品身份、策略身份、建议值/动作域和终态枚举映射。

因为数据字典尚未显示“每条明细的执行状态、完成时间、广告实体/对象、历史动作类型和建议值”的物理字段，接入后必须在 JSON 或关联表中补齐它们的可靠来源；若无法唯一取得，正向动作写 `history_mapping_pending`，而不是假定无历史。广告级历史策略状态核验尤其不能只凭 SKU 明细表放行。

## 6. 公共数据标准化层

在角色规则运行前，先构建下列逻辑层；它们可以是 CTE、中间表或视图，但必须有同样的输入与输出语义。

| 逻辑层 | 输入 | 输出/责任 |
|---|---|---|
| `source_freshness` | 全部来源 | 每源最大日期、选用日期、是否可比、缺失原因。 |
| `product_identity` | 标签、经营、定价、库存 | 统一 `country + store + msku`，并标记 ASIN、店铺、国家是否唯一。 |
| `product_metrics` | 成本/经营快照 | 销量、日销、利润、利润率、产品 TACOS 和成本质量。所有指标记录来源日期与窗口。 |
| `price_lines` | 定价表 | 当前价、各利润价格线、价格异常状态。 |
| `inventory_metrics` | DWD FBA 库存明细 | 按 `country_category + store + msku` 汇总的 `afn_fulfillable_quantity`、快照时间、共享 DOS 和库存映射状态。 |
| `ad_object_metrics` | SP 对象快照 | 可投放状态、对象身份、映射状态、成熟表现、当前 bid。 |
| `search_term_metrics` | 搜索词快照 | 标准化搜索词、来源、保护状态、成熟表现。 |
| `budget_metrics` | 预算分析表 | 月/周预算、剩余预算、预算状态、共享归因/映射状态。 |
| `history_strategy_check` | 历史审核表 | 每个候选动作的已完成/待完成/复盘中/待核结论。 |

其中 `product_metrics` 需要显式选择利润率和 TACOS 公式，并将分子、分母、窗口天数与质量状态保留在证据中。例如，在角色规则明确采用订单利润口径时，可用：

```text
日销 = 近30天销量 ÷ 实际统计窗口天数
订单利润率 = 近30天订单毛利润_cny ÷ 近30天净销售额_cny
产品 tacos = 广告成本_cny ÷ 近30天净销售额_cny
```

分母为 0、窗口不完整、利润口径未确认或成本对账不通过时，不能生成依赖这些指标的数值正向动作。

库存 DOS 另按共享库存池计算，不能拿同一库存分别除以德国、法国等单国日销：

```text
共享日销 = 同一 country_category + store + msku 下所有国家产品日销之和
共享基础 dos = afn_fulfillable_quantity ÷ 共享日销
共享目标 dos = afn_fulfillable_quantity ÷ 同一库存池内所有受影响国家的目标日销之和
```

国家级建议仍保留各自的 `country`，但所有正向动作须先汇总到同一个共享库存池判断。若共享 DOS 只允许 1 个拉量动作，则德国和法国的候选动作合计也只能保留 1 个；不能让每个国家各自占用一次动作额度。

## 7. 新销售角色规则文档的输入契约

每份角色规则文档必须补齐以下内容，通用开发人员才能无歧义接入：

| 必填项 | 应明确的内容 |
|---|---|
| 策略身份 | `strategy_scope`、业务名称、`rule_version`、生效日期。 |
| 规则目录 | 每条可输出规则的 `strategy_rule_id`、数字 `rule_code`、展示名称、动作说明与观察期；未建档规则不得上线。 |
| 样本准入 | 标签/名单来源、标签周期、国家范围、产品粒度及各标签的关联键。 |
| 主指标 | 销量、日销、利润/毛利、TACOS/ACOS、价格、库存的唯一来源、公式、窗口与缺失处理。 |
| 路径表 | 路径优先级、准入条件、目标、退出条件、下转/上转规则。 |
| 价格规则 | 可否调价、价格线名称、上下限、每轮幅度或阶梯、价格缺失处理。 |
| 广告规则 | 广告未开、零花费、低效、有效对象的判断；对象阈值、bid/加词/否词/暂停规则、互斥关系。 |
| 成本规则 | 触发成本诊断的条件、所需八项成本口径、纵向/横向判断可用性。 |
| 库存与预算 | 库存池粒度、DOS 公式、各库存档位限制、跨国家共享库存时的动作合并规则、预算池来源、可扩量条件、预算上限。 |
| 历史与复盘 | 哪些动作是同类动作、终态后 D+3/D+7/D+14/30 天的适用窗口、止损是否可绕过历史阻断。 |
| 输出映射 | 每个规则的 `strategy_rule_id`、`rule_code`、`decision_type` 或 `action_type`、动作上限及必须写入的独立字段。 |

未明确以上任一项时，开发应先标为待确认，不能从其他角色规则中猜测阈值或动作。

## 8. 历史策略状态核验

历史策略状态核验按“批次执行状态 + SKU 明细复盘结果”组合判断。已确认物理字段中，批次表 `status` 是运行状态来源，明细表 `outcome` 是 SKU 结果来源；两者职责不能互换。即使批次到达终态，也不能仅凭此假定每个 SKU 都已达成或已具备再次执行条件。

| 状态 | 条件 | 新建议处理 |
|---|---|---|
| `no_history` | 没有匹配的历史策略项 | 进入后续角色规则。 |
| `waiting_history_complete` | 找到同类历史明细，所属批次 `status` 尚未映射为终态 | 阻断同类新正向动作和重复调价。 |
| `in_review_window` | 所属批次已到终态，但仍处在角色指定复盘期或批次观察到期前 | 不生成新的正向动作，写 `next_review_date`。 |
| `eligible_after_review` | 批次已到终态、复盘窗口结束，且该 SKU 的 `outcome` 已按确认映射通过 | 基于最新数据重新判断。 |
| `history_mapping_pending` | 历史项或广告对象无法唯一关联 | 禁止正向动作；是否允许止损由角色规则决定。 |
| `history_source_unavailable` | 历史表连接或字段适配不可用 | 禁止正向动作；不能把它误写成无历史。 |

建议的匹配顺序：先以 `selection_key`（经生成规则核验后）匹配，再按 `site_code + store_name + sku` 规范化匹配，并以策略身份、动作域收窄。产品动作可用 ASIN 辅助核验。广告动作必须额外取得 `profile + campaign + ad_group + entity + object + normalized_search_term` 的可靠历史来源；当前两张截图未显示这些字段时，不得将 SKU 级历史误用于广告对象级放行。多条等优先历史项不得任选一条。

## 9. 动作键、幂等与版本

广告 `action_key` 应基于规范化字段稳定生成：

```text
sha256(
  data_date | strategy_scope | rule_version | country | store | msku |
  action_type | profile_id | campaign_id | ad_group_id |
  ad_entity_type | ad_entity_id | object_type | object_id | normalized_search_term
)
```

空值使用明确占位符参与计算。搜索词必须先做大小写、首尾空格和匹配类型标准化，不能只用 MSKU 或活动 ID 当键。

- 产品表按 `data_date + strategy_scope + rule_version + country + store + msku` 幂等更新。
- 广告表按 `data_date + strategy_scope + rule_version + action_key` 幂等更新。
- 同日、同版本重跑更新稳定字段、证据和 `updated_time`，不得重复插入。
- 跨日期、跨策略域、跨规则版本保留历史快照。
- 规则版本升级不会绕过旧策略项的未完成或复盘窗口状态。

## 10. 开发实施流程

### 阶段 0：接入前核验

1. 读取本通用文档、新角色规则文档和 `dws_datasync.dws_product_strategy_rule_config`，逐项填完第 7 节输入契约，并校验每个可输出规则均已建档。
2. 在目标环境执行 `information_schema` 字段检查，确认本节字段仍存在。
3. 接入历史审核数据源，完成批次 `status` 终态、SKU `outcome` 枚举、观察窗口和动作身份映射。
4. 选取至少 10 条人工已知样本，明确预期建议或阻断结果；首批候选与确认格式见 [产品运营建议验收样例集](产品运营建议验收样例集.md)。

### 阶段 1：源数据与标准化层

1. 先计算每个来源的最大可用日期与数据状态；确定共同 `data_date`。
2. 建产品身份底表，检查 `country + store + msku` 是否唯一、标签/店铺/ASIN 是否冲突。
3. 建经营、价格、库存、广告对象、搜索词、预算标准化层，并为每个字段保留来源日期和质量状态；库存先按 `country_category + store + msku` 汇总为共享库存池，再关联各国家产品记录。
4. 对成本、价格、库存、广告映射和预算分别实现待核状态，不能用默认 0 代替缺失值。

### 阶段 2：历史与策略规则

1. 先产生“候选产品决策”和“候选广告动作”，为每条候选计算历史匹配键。
2. 应用历史策略状态核验；未完成、复盘中、来源不可用或匹配不唯一的记录不得进入新正向动作计算。
3. 仅对允许记录应用新角色的样本、路径、价格、成本、广告、库存和预算规则，并将每条命中候选绑定到唯一的 `strategy_rule_id + rule_code`。
4. 先保留止损类动作，再按共享库存池汇总所有国家的正向候选，应用正向动作数量、共享 DOS 和预算上限；互斥动作只能保留优先级最高的一条。

### 阶段 3：结果输出

1. 每个产品在产品表输出一条主结论，即使结论是待核、库存拦截或维持价格。
2. 每个可审核广告动作写广告表一条；不把多对象动作拼接在同一行。
3. 数值动作没有通过必经数据闸门时，`suggested_price` 或 `suggested_value` 保持为空。
4. 执行幂等写入，并输出当日按 `strategy_scope`、路径、`rule_code`、`data_status`、历史状态统计的审计计数。

### 阶段 4：每日运行与变更

1. 在既定快照节奏满足后运行：标签和广告取 `D-1`，价格、成本、库存、预算取 `D`。若任一来源不满足对应日期或无明确滞后口径，输出数据待核并告警，不回退到无说明的旧日期。
2. 每日只读历史策略表，不回写结果表以外的系统。
3. 新角色接入只增加策略适配和规则配置；公共字段、历史策略状态核验和幂等逻辑不复制。
4. 规则阈值、价格线、广告动作或状态枚举变化时提高 `rule_version`，并保留历史版本快照。

## 11. 验收清单

### 11.1 数据与关联

- [ ] 标签、经营、定价、库存、广告、预算均记录实际采用日期。
- [ ] 标签/广告为 `D-1`、价格/成本/库存/预算为 `D` 时可正常通过日期闸门；只有偏离既定节奏、成本对账异常、价格线缺失、库存缺失、广告映射不唯一或预算映射不清才产生独立 `data_status`。
- [ ] 不用空值或 0 掩盖缺失；不向下游输出伪精确数值动作。
- [ ] 库存按仓库汇总后才参与 DOS，并不将实际在途计入可售 DOS，除非角色规则另有明确授权。

### 11.2 历史与幂等

- [ ] 无历史、未完成、完成但复盘中、复盘结束、历史源不可用、历史匹配不唯一均有覆盖。
- [ ] 父批次完成而策略项未完成时，仍正确阻断。
- [ ] 同日同版本重跑后主键数不增加；跨日期和跨版本保留。
- [ ] `action_key` 可重算，并能区分同一活动内不同对象和搜索词。

### 11.3 规则与输出

- [ ] 每个角色规则都有样本、路径、目标、退出、价格、广告、成本、库存、预算、历史窗口和验收案例，且每个可输出规则已登记在策略规则目录表。
- [ ] 每个正向动作都经过数据、历史、库存、预算和动作上限检查。
- [ ] 每个止损动作的历史/库存例外有角色规则明确授权。
- [ ] 产品表始终一产品一主结论；广告表一行一原子动作。
- [ ] `evidence_json` 合法但不要求固定结构，稳定筛选字段不隐藏在 JSON 中。
