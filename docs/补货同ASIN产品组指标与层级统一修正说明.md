> 修正日期：2026-08-04
>
> 测试分支：`codex/replenishment-lead-time-test`
>
> 测试库：`etl_datasync_replenishment_test`
>
> 测试页面：`http://127.0.0.1:8002/replenishment`

## 一、结论与本次改动

本次修正解决的是：同一个国家、同一个品类、同一个 ASIN 下的主链接和跟卖链接，明明属于同一个产品、库存也应当共享，但页面上可能出现“库存支撑天数使用合并库存，补货层级却使用单链接库存”的口径混用。例如页面显示库存可支撑 **80.19 天**、到货时仍可支撑 **70.19 天**，标签却显示“紧急补货”，容易让人误以为分层计算错误。

修正后，同一产品组内的所有链接统一展示产品组口径：

- 库存可支撑天数一致；
- 采购交期一致；
- 到货时支撑天数一致；
- 补货层级一致；
- 交期预计消耗、到货预计库存、预计断货天数等交期指标一致；
- 仍然只给选定的目标链接分配实际补货数量、箱数和金额，其他链接的补货数量保持为 0，避免重复补货。

因此，本次改动统一的是**产品组的判断与展示口径**，没有把一组产品拆成多份补货，也没有改变“一个产品组只向一个目标链接下单”的原则。

## 二、问题是怎么产生的

原有逻辑同时存在两套计算范围：

1. 单链接口径：每条主链接或跟卖链接根据自己的库存计算原始支撑天数和补货层级；
2. 产品组口径：相同 `国家 + 品类 + ASIN` 的链接合并库存，再判断产品组是否需要补货以及需要补多少。

随后在结果落库和接口展示时，这两套口径被组合在同一行中：

- 库存可支撑天数和到货时支撑天数可能来自产品组；
- “紧急补货、建议补货、计划补货”等层级标签可能仍来自目标链接自己的库存；
- 部分合并组内补货数量为 0 的链接，还会被接口额外改成“库存充足”。

这就造成了同一行上的数值和标签并不是根据同一份库存计算的。计算本身不一定错，真正的问题是**展示范围不一致**。

## 三、新旧规则对比

| 项目 | 修正前 | 修正后 |
| --- | --- | --- |
| 产品组范围 | 同国家、同品类、同 ASIN | 不变 |
| 是否合并库存 | 补货决策和数量会合并 | 不变 |
| 库存支撑天数展示 | 部分行使用组数据，部分场景仍带单链接口径 | 组内所有链接统一使用组数据 |
| 到货时支撑天数 | 主要在目标链接上使用组数据 | 组内所有链接统一使用组数据 |
| 补货层级 | 可能保留各链接自身层级 | 组内所有链接统一使用产品组层级 |
| 非目标链接层级 | 可能因补货量为 0 被显示为库存充足 | 保留产品组真实层级，不再强制改成库存充足 |
| 补货数量 | 只分配给目标链接 | 不变，仍只分配给目标链接 |
| 箱数和金额 | 只分配给目标链接 | 不变 |
| 防止重复下单 | 产品组只能有一个有效补货目标 | 不变 |

## 四、最终计算规则

### 4.1 产品组的识别

可以合并的链接按以下字段组成一个产品组：

```text
国家 + 产品分类 + 最大 ASIN（max_asin）
```

只有满足 ASIN 合并条件的记录才使用产品组口径；普通、不参与合并的 SKU 继续使用原有单品计算结果。

### 4.2 产品组库存与日销

产品组库存为组内可用于补货判断的库存合计，产品组日销沿用现有 ETL 中确定的组日销口径。

```text
产品组库存可支撑天数 = 产品组可用库存 ÷ 产品组日销
```

当日销为 0 时，沿用现有防除零和业务兜底逻辑，不在本次改动中重新定义日销算法。

### 4.3 采购交期

```text
有效采购交期 = 已配置的采购交期
```

采购交期为 0 表示未配置，按 **0 天**参与计算，不再默认替换成 10 天。

### 4.4 到货时支撑天数

“到货时支撑”表示：假设今天下单，在采购交期内继续销售，等货到达时，现有库存预计还能支撑多少天。

```text
到货时支撑天数 = 产品组库存可支撑天数 - 有效采购交期
```

例如产品组当前可支撑 80.19 天，采购交期 10 天：

```text
到货时支撑天数 = 80.19 - 10 = 70.19 天
```

如果结果为负数，说明预计会在新货到达前断货：

```text
预计断货天数 = max(0, 有效采购交期 - 产品组库存可支撑天数)
```

例如库存仅可支撑 9 天、采购交期为 10 天，则到货时支撑天数为 -1 天，预计断货 1 天。

### 4.5 补货层级

产品组层级由产品组统一指标判断，不再由某一条主链接或跟卖链接自己的库存单独决定。分层阈值仍沿用当前补货 ETL 已有配置，本次没有调整紧急补货、建议补货、计划补货和库存充足之间的阈值。

本次只修正两点：

1. 组内所有链接使用同一产品组层级；
2. 不再因为某条非目标链接的补货数量为 0，就把它强制显示为“库存充足”。

### 4.6 补货数量

补货需求仍按产品组计算，并结合采购交期覆盖交期内预计销量。计算出的产品组需求只分配给一个补货目标链接：

```text
产品组补货需求 → 目标链接：实际补货数量、箱数、金额
             → 其他链接：补货数量为 0
```

所以，同一组中的主链接和跟卖链接会显示相同的支撑天数和补货层级，但不会每条链接都产生一份补货数量。

## 五、直观案例

### 5.1 QP122b：为什么 80.19 天不应显示紧急补货

修正前，同组两条链接大致表现为：

| 链接 | 单链接库存 | 单链接日销 | 单链接支撑 | 单链接到货时支撑 | 原单链接层级 |
| --- | ---: | ---: | ---: | ---: | --- |
| Qipunike | 120 | 2.244762 | 53.46 天 | 43.46 天 | 建议补货 |
| Quankezhan | 60 | 2.244762 | 26.73 天 | 16.73 天 | 紧急补货 |

但两条链接属于同一个产品，库存应合并为 180 件：

```text
产品组当前支撑 = 180 ÷ 2.244762 = 80.19 天
产品组采购交期 = 10 天
产品组到货时支撑 = 80.19 - 10 = 70.19 天
```

原页面可能把产品组的 **80.19/70.19 天**与目标链接自己的“紧急补货”标签放在一起，因此看起来矛盾。

修正后，两条链接统一显示：

| 指标 | 修正后结果 |
| --- | ---: |
| 库存可支撑天数 | 80.19 天 |
| 采购交期 | 10 天 |
| 到货时支撑天数 | 70.19 天 |
| 补货层级 | 计划补货 |
| 实际正补货目标数 | 1 个 |
| 目标链接补货数量 | 120 件 |
| 另一链接补货数量 | 0 件 |

### 5.2 QP0102b：组内指标统一，但不会重复补货

测试库重算后，该产品组的两条欧洲链接统一为：

| 指标 | 两条链接统一结果 |
| --- | ---: |
| 库存可支撑天数 | 65.95 天 |
| 采购交期 | 20 天 |
| 到货时支撑天数 | 45.95 天 |
| 补货层级 | 建议补货 |

实际补货仍只落在目标链接 Quankezhan 上：

| 链接角色 | 补货数量 |
| --- | ---: |
| 目标链接 Quankezhan | 150 件 |
| 同组另一链接 | 0 件 |

这说明“所有链接统一展示产品组状态”和“只向一个链接补货”可以同时成立。

## 六、代码修改范围

### 6.1 ETL 结果落库

文件：`etl/replenishment_update.py`

- 最终结果使用统一后的 `final_inventory_support_days`；
- 对所有满足 `asin_merge_flag = 1` 的组内链接应用产品组指标，不再只对补货目标链接应用；
- 产品组补货层级名称和排序统一计算并写入结果；
- 补货数量、箱数、金额仍以目标链接标识为准，非目标链接保持为 0。

### 6.2 页面数据接口

文件：`app/services/replenishment_data.py`

- 删除“合并组内补货数量为 0 就显示库存充足”的覆盖逻辑；
- 页面直接使用 ETL 已统一的产品组层级和排序；
- 避免接口层再次改变 ETL 的业务判断结果。

### 6.3 自动化测试

- `tests/test_replenishment_update_sql.py`

- 非目标链接即使补货量为 0，也保留产品组真实层级；
- 层级流转统计使用统一后的产品组层级；
- 普通、不参与 ASIN 合并的 SKU 继续使用原有结果。

## 十、风险与后续注意事项

1. 本次重算只针对测试库，正式库历史快照不会自动变化；正式环境启用前仍需按发布流程执行 ETL 和抽样核对。
2. 如果后续调整日销、库存范围、层级阈值或产品组识别字段，需要重新验证组内统一指标和单目标补货约束。
3. “组内所有链接显示相同层级”不代表每条链接都要下单；补货数量列仍应以目标链接为准。
4. 采购交期为 0 表示未配置并按 0 天计算，这一口径需要在后续配置治理中保持一致。

## 十二、最终验收口径

上线或再次重算后，只要同时满足以下条件，即可认为本次修正生效：

- 同一产品组内所有链接的库存支撑天数一致；
- 同一产品组内所有链接的采购交期一致；
- 同一产品组内所有链接的到货时支撑天数一致；
- 同一产品组内所有链接的补货层级一致；
- 一个产品组最多只有一个链接产生正补货数量；
- 普通 SKU 的结果未受影响；
- 页面展示结果与导出结果使用相同口径。
