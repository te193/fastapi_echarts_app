# 方案8：低销量 SKU 单日大跳变拦截详细规划

## 1. 目标

解决低销量 SKU 因为单日 1 单导致支持天数剧烈变化，从而从“库存充足”直接跳到“紧急补货”的问题。

核心目标不是修改日销计算，也不是修改原始支持天数，而是在补货分层上增加一层“低销量单日跳变保护”。

希望达到的效果：

```text
正常动销商品：继续按当前逻辑分层，不受影响。
低销量商品：如果只是因为单日 1 单导致从库存充足跳到紧急，不立即进入紧急补货。
真实起量商品：如果连续动销、库存真的危险，仍然可以进入紧急补货。
```

## 2. 当前问题复盘

以 `DY-057a` 为例：

```text
2026-07-05：
支撑库存 = 4
计算日销 = 0.006667
支持天数 = 600.00
分层 = 库存充足

2026-07-06：
支撑库存 = 3
计算日销 = 0.113333
支持天数 = 26.47
分层 = 紧急补货
```

变化原因：

```text
2026-07-05 德国卖出 1 件
最近 3 天销量从 0 变 1
最近 7 天销量从 0 变 1
最近 14 天销量从 0 变 1
30 天销量从 1 变 2
```

由于当前老品日销公式偏重 7 天窗口：

```text
日销 = 7天日销 * 0.6 + 14天日销 * 0.2 + 30天日销 * 0.2
```

所以 1 单会明显抬高计算日销，最终把支持天数压低。

这类情况的本质是：

```text
销量样本太少，不代表真实稳定起量。
```

## 3. 方案原则

### 3.1 不改原始日销

原始日销仍按当前逻辑计算。

原因：

```text
日销字段本身有分析价值。
如果直接改日销，会影响产品分类、补货数量、毛利表现等多个链路。
```

### 3.2 不改原始支持天数

支持天数字段仍展示真实计算结果。

例如：

```text
DY-057a 当天支持天数仍显示 26.47
```

这样用户仍能看到短期销量变化。

### 3.3 只拦截补货分层的大跳变

新增一个“保护后分层”或直接在补货计算中使用保护后的分层。

也就是说：

```text
原始分层：紧急补货
保护后分层：计划补货 / 观察
```

补货数量、补货金额、补货件数以保护后分层为准。

### 3.4 保护只针对低销量 SKU

高销量、正常动销 SKU 不走保护逻辑。

例如：

```text
30天销量 >= 5
或最近7天销量 >= 2
或今日销量 >= 2
```

这类应该认为风险更可信，不做拦截。

## 4. 核心规则设计

### 4.1 低销量定义

建议第一版使用简单、可解释的低销量定义：

```text
30天销量 <= 3
```

可以同时加一个辅助条件：

```text
最近7天销量 <= 1
```

完整低销量条件：

```text
30天销量 <= 3
且 最近7天销量 <= 1
```

解释：

```text
30天销量 <= 3：说明长期销量基数低。
最近7天销量 <= 1：说明没有明显连续起量。
```

### 4.2 单日大跳变定义

建议第一版只拦截最极端、最容易误判的跳变：

```text
昨日分层 = 库存充足
今日原始分层 = 紧急补货
```

对应排序字段：

```text
昨日 support_replenish_level_sort = 4
今日原始 support_replenish_level_sort = 1
```

也可以预留扩展：

```text
昨日库存充足，今日建议补货：暂不拦截
昨日计划补货，今日紧急补货：暂不拦截
```

第一版只处理“4 到 1”的大跳变，避免影响面过大。

### 4.3 今日销量限制

为了防止真实爆单被误拦截，需要判断今日销量。

建议：

```text
今日销量 <= 1 才允许拦截
```

如果今日销量大于等于 2：

```text
说明短期动销已经不是单个偶发订单，不拦截。
```

### 4.4 库存安全豁免

如果库存已经非常危险，不应该拦截。

建议：

```text
支撑库存 <= 1 不拦截
```

解释：

```text
低销量 SKU 也可能断货。
如果只剩 0 或 1 件，即使低销量，也应该进入紧急或建议补货。
```

对于 `DY-057a`：

```text
支撑库存 = 3
可以拦截
```

### 4.5 连续低支持天数豁免

如果连续两天都低于紧急阈值，说明风险不是单日偶发。

建议：

```text
如果昨日支持天数 <= 35，今日支持天数 <= 35，不拦截
```

解释：

```text
第一天保护，第二天确认风险。
```

### 4.6 推荐第一版完整规则

当同时满足以下条件时，触发保护：

```text
昨日分层 = 库存充足
今日原始分层 = 紧急补货
30天销量 <= 3
最近7天销量 <= 1
今日销量 <= 1
支撑库存 > 1
昨日支持天数 > 35
```

触发保护后：

```text
保护后分层 = 计划补货
保护后分层排序 = 3
```

为什么建议降到计划补货，而不是库存充足：

```text
因为今日支持天数确实已经变低，完全当库存充足不合理。
计划补货能提示采购关注，但不会按紧急补货直接放大处理。
```

## 5. 字段设计

为了可追踪，建议不要只覆盖原字段，最好增加保护字段。

### 5.1 建议新增字段

```text
raw_support_replenish_level
raw_support_replenish_level_sort
support_jump_guard_flag
support_jump_guard_reason
guarded_support_replenish_level
guarded_support_replenish_level_sort
```

字段含义：

```text
raw_support_replenish_level：原始分层
raw_support_replenish_level_sort：原始分层排序
support_jump_guard_flag：是否触发跳变保护，1 是，0 否
support_jump_guard_reason：触发原因说明
guarded_support_replenish_level：保护后分层
guarded_support_replenish_level_sort：保护后分层排序
```

### 5.2 如果想少改字段

也可以只增加两个字段：

```text
support_jump_guard_flag
support_jump_guard_reason
```

然后原 `support_replenish_level` 直接保存保护后的分层。

但这种方式会丢失原始分层，不利于排查。

### 5.3 推荐做法

推荐保留原始分层和保护后分层：

```text
原始分层用于解释模型结果。
保护后分层用于补货决策和看板主展示。
```

如果页面暂时不想改复杂，可以主展示保护后分层，抽屉或明细字段显示原始分层和保护原因。

## 6. 数据流设计

### 6.1 当前链路

简化后的当前链路：

```text
计算日销
-> 计算支持库存
-> 计算支持天数
-> 按支持天数生成补货分层
-> 根据分层决定补货数量
```

### 6.2 新链路

加入方案 8 后：

```text
计算日销
-> 计算支持库存
-> 计算支持天数
-> 按支持天数生成原始补货分层
-> 读取昨日分层和昨日支持天数
-> 判断是否触发低销量单日大跳变保护
-> 生成保护后补货分层
-> 根据保护后分层决定补货数量
```

### 6.3 插入位置

建议插在：

```text
tmp_pur_plan_support_layer_all
```

和：

```text
tmp_pur_plan_replenish_calc
```

之间。

原因：

```text
tmp_pur_plan_support_layer_all 已经有支持天数和原始分层。
tmp_pur_plan_replenish_calc 会根据分层继续计算补货需求。
```

也就是说，在进入最终补货数量计算前，把分层保护处理好。

## 7. 昨日数据依赖

### 7.1 昨日结果来源

从结果表查昨日同一 SKU：

```text
dashboard_pur_plan_replenish_data
```

匹配维度：

```text
country_category
seller_name_new
seller_sku_adj
cur_date = 当前 cur_date - 1
```

### 7.2 如果昨日数据不存在

建议：

```text
不触发保护
```

原因：

```text
没有昨日分层，无法确认是否是单日大跳变。
贸然保护可能漏掉真实风险。
```

### 7.3 如果昨日也是紧急

建议：

```text
不触发保护
```

原因：

```text
说明不是从库存充足突然跳到紧急，而是风险持续存在。
```

## 8. 今日销量口径

### 8.1 推荐口径

今日销量建议使用业务日期当天销量：

```text
biz_date 当天 sales_qty
```

聚合维度：

```text
country_category
seller_name_new
seller_sku_adj
```

### 8.2 如果没有单独今日销量字段

可以用窗口销量反推：

```text
today_sales = 今日业务日期在 dashboard_product_performance_daily 的 sales_qty 汇总
```

不建议用：

```text
3天销量
```

原因：

```text
3天销量可能包含前两天，不够精确。
```

## 9. 分层结果建议

### 9.1 保护后降到哪一层

建议第一版降到：

```text
计划补货
```

排序：

```text
3
```

原因：

```text
完全保持库存充足会忽略风险。
降到建议补货仍然可能触发较强补货动作。
计划补货能起提醒作用，又不会太激进。
```

### 9.2 是否影响补货数量

建议影响。

也就是说：

```text
补货数量根据保护后分层计算。
```

如果保护后分层是计划补货：

```text
仍可能计算补货数量。
```

如果业务希望保护后只观察、不补货，则可以把保护后分层设为库存充足或新增观察层。

### 9.3 更保守版本

如果希望触发保护后不产生补货数量：

```text
保护后分层 = 库存充足
```

但不推荐第一版这样做，容易漏掉真实低库存风险。

## 10. 示例说明

### 10.1 示例一：DY-057a

输入：

```text
昨日分层 = 库存充足
昨日支持天数 = 600
今日原始分层 = 紧急补货
今日支持天数 = 26.47
30天销量 = 2
7天销量 = 1
今日销量 = 1
支撑库存 = 3
```

判断：

```text
昨日库存充足 -> 今日紧急，命中大跳变
30天销量 <= 3，命中低销量
7天销量 <= 1，说明没有明显连续起量
今日销量 <= 1，说明只是单日 1 单
支撑库存 > 1，库存没有危险到必须立刻紧急
```

结果：

```text
原始分层 = 紧急补货
保护后分层 = 计划补货
保护标记 = 1
保护原因 = 低销量SKU单日1单导致库存充足跳紧急，降级为计划补货观察
```

达到的效果：

```text
避免从 600 天直接进入紧急补货。
仍保留计划补货提醒。
```

### 10.2 示例二：低销量但库存只剩 1 件

输入：

```text
昨日分层 = 库存充足
今日原始分层 = 紧急补货
30天销量 = 2
7天销量 = 1
今日销量 = 1
支撑库存 = 1
```

判断：

```text
支撑库存 <= 1，不允许拦截
```

结果：

```text
保护标记 = 0
最终仍为紧急补货
```

达到的效果：

```text
低销量商品也不会因为保护规则错过真实断货风险。
```

### 10.3 示例三：低销量但今日突然卖 3 件

输入：

```text
昨日分层 = 库存充足
今日原始分层 = 紧急补货
30天销量 = 4
7天销量 = 3
今日销量 = 3
支撑库存 = 3
```

判断：

```text
今日销量 > 1，不触发保护
30天销量也已经 > 3，不属于低销量保护范围
```

结果：

```text
保护标记 = 0
最终仍为紧急补货
```

达到的效果：

```text
真实起量的商品仍能及时补货。
```

### 10.4 示例四：连续两天都是紧急

输入：

```text
昨日分层 = 紧急补货
昨日支持天数 = 28
今日原始分层 = 紧急补货
今日支持天数 = 26
30天销量 = 3
今日销量 = 1
支撑库存 = 3
```

判断：

```text
昨日不是库存充足，不属于单日大跳变。
连续两天低支持天数，应承认风险。
```

结果：

```text
保护标记 = 0
最终仍为紧急补货
```

达到的效果：

```text
第一天可以保护，第二天仍然危险时不继续拦截。
```

## 11. 页面展示建议

### 11.1 主列表

主列表建议展示保护后分层。

例如：

```text
计划补货
```

### 11.2 明细或提示

可以增加一个提示字段：

```text
原始分层：紧急补货
保护原因：低销量SKU单日1单导致库存充足跳紧急，已降级观察
```

这样业务人员能知道：

```text
系统不是没看到紧急风险，而是做了低销量保护。
```

### 11.3 筛选

可以增加筛选项：

```text
已触发跳变保护
```

方便后续复盘这些 SKU 是否被保护得合理。

## 12. 通知和日志建议

### 12.1 ETL 日志

每天 ETL 输出：

```text
低销量跳变保护触发数：N
其中 库存充足 -> 紧急 被降级为计划补货：N
```

### 12.2 钉钉通知

不建议每天推详细 SKU。

可以只放汇总：

```text
低销量跳变保护：23 个 SKU
```

如果失败或异常，再提示检查。

### 12.3 复盘 SQL

保留字段后，可以通过 SQL 复盘：

```text
where support_jump_guard_flag = 1
```

至少准备 5 类样例：


重点看：


## 14. 上线策略

### 14.1 第一阶段：影子模式

先不影响实际分层，只计算：

```text
support_jump_guard_flag
guarded_support_replenish_level
guarded_support_replenish_level_sort
```

看板主逻辑仍用原始分层。

观察 1-3 天：

```text
每天触发多少 SKU
这些 SKU 是否确实不该紧急
保护后补货数量会减少多少
```

### 14.2 第二阶段：正式启用

确认合理后：

```text
补货数量使用保护后分层
主列表展示保护后分层
明细保留原始分层和保护原因
```

### 14.3 回滚方式

保留开关：

```text
ENABLE_LOW_SALES_JUMP_GUARD=1
```

如果发现误判：

```text
改为 0，恢复原始分层逻辑
```

## 15. 推荐参数

第一版建议参数：

| 参数 | 推荐值 | 说明 |
| --- | ---: | --- |
| 低销量30天销量阈值 | 3 | 30天卖3件以内认为样本太少 |
| 最近7天销量阈值 | 1 | 7天只卖1件以内认为没有明显起量 |
| 今日销量阈值 | 1 | 今日只卖1件以内才认为可能偶发 |
| 库存危险豁免 | <= 1 | 库存0或1件不拦截 |
| 拦截跳变范围 | 库存充足 -> 紧急补货 | 第一版只处理最大跳变 |
| 保护后分层 | 计划补货 | 不完全忽略风险 |

## 16. 最终推荐版本

推荐最终规则如下：

```text
如果：
  昨日分层 = 库存充足
  且 今日原始分层 = 紧急补货
  且 30天销量 <= 3
  且 最近7天销量 <= 1
  且 今日销量 <= 1
  且 支撑库存 > 1
  且 昨日支持天数 > 35

则：
  support_jump_guard_flag = 1
  原始分层保留为紧急补货
  保护后分层改为计划补货
  补货数量按计划补货逻辑继续计算
```

如果不满足任一条件：

```text
不触发保护
继续使用原始分层
```

## 17. 预期影响

对 `DY-057a` 这类 SKU：

```text
原始结果：紧急补货，补货 50
保护后：计划补货或观察，避免被当成真实紧急
```

对正常商品：

```text
30天销量较高，不触发保护
今日销量较高，不触发保护
库存很低，不触发保护
连续两天紧急，不触发保护
```

整体预期：

```text
紧急补货数量会减少一部分低销量偶发 SKU。
补货建议会更稳。
不会明显影响真实高动销缺货商品。
```
