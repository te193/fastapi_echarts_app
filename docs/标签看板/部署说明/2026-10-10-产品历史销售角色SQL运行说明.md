# 产品历史销售角色 SQL 运行说明

这套脚本把每个产品从上架起的经营历史切成连续、互不重叠的 30 天段，按现行 V47 标准回算角色，并保存有效完整段中出现次数最多的主导角色。历史主导角色表示经营类型，不等于当年的实际标签，也不等于已执行的运营决策。

运行模式固定为：**第一次 `bootstrap` 全量计算，之后使用 `incremental` 仅计算最近未完成段及新增段**。日常任务不要重复调用 `bootstrap`；数据回补或规则/起点修正才使用显式 `rebuild`。

日常增量的验收目标为 **10 分钟以内**；首次全量单独计时。首次首算中断时，应先重试并完成首算，过程会阻止直接切换到增量，避免遗漏尚未发布的历史商品。

规则依据为项目内 [V47 基线 SQL](../../../sqlcode/标签表数据插入_修改版_20261008_v47_接收中归入断货中修复版.sql) 的全站点和国家站点实际分类表达式，并参考此前只读核对的远端标签证据；不以本地旧分类器或字典说明文字替代计算条件。

用户已将 opt 试跑结果迁移到正式 `dws_datasync`。当前修改仅更新本地交付代码并在隔离库验证，远端只读核对，由用户部署运行。此前按授权在远端 `opt_db` 使用独立试跑对象验证全量与增量；源表和现有标签表仅查询。本地边界验证使用仅监听回环地址的 MySQL 8.0.46 和合成数据。

## 一个文件与执行顺序

只使用 [完整 SQL 文件](../../../sqlcode/2026-10-10-产品历史销售角色建表与计算.sql)。文件分为五段：第1段部署，第2段历史首算，第3段日常增量，第4段指定区间重算，第5段只读验收。

第2—5段包装在块注释里，全文件执行只会部署，不会同时进行首算、增量和重算。需要运行时，在支持 `delimiter` 的 MySQL 客户端中选中对应块注释内部的 SQL 正文执行，不包含外层 `/*`、`*/`。日期和产品参数默认留空，填完再运行。第1段使用 DBeaver“执行 SQL 脚本”或 MySQL CLI 的 `source`，不要将存储过程正文逐行执行。

首次顺序为第5段部署前检查 → 第1段部署 → 第2段首算 → 第5段结果验收；后续只运行第3段，修正历史时按需运行第4段。

## 部署前检查

1. 使用新建的独立连接，`autocommit=1`，没有外部事务。过程会自行提交，不能包在应用事务中运行。
2. MySQL 版本要求 8.0.21 及以上。读取 `dwd_datasync` 的权限，以及在 `dws_datasync` 对新对象执行 `create`、`alter`、`create routine`、`alter routine`、`execute`、`insert`、`update`、`create temporary tables` 的权限必须满足。过程采用 `sql security invoker`，调用者也须具备相应权限。
3. 源表为 `lx_statistics_product_performance_2020` 至 `_2025`、无年份后缀的 `lx_statistics_product_performance`，以及 `lx_sales_mws_listing`。先执行第5段的结构和日期覆盖部分。日级表现应满足 `start_date=end_date`；身份超长、空身份、非日级记录会中止计算，不能默默截断或当成零销量。
4. 当前续表必须有以 `start_date` 为第一列的索引。当前库已只读核验存在 `idx_osp_performance_date_sync`；过程优先使用它，否则选择其他日期首列索引。没有可用索引时普通增量停止，不自动修改源表。年度历史表使用已有主键 `id` 分批读取。
5. 首算和指定重算的截止日由人工核验完整性后填写。按 2026-10-12 用户确认，日常定时入口改为读取产品表现续表的 `max(start_date)`，与所有结果记录的截止日比较；不依赖同步日志。过程仍检查最近 7 个自然日有源记录，但最新日期存在不等于所有店铺已同步完整。建议定时任务放在日常同步之后；同日期内回补或修改不会自动触发重算。

部署脚本只修改本方案的新对象，现有标签表、现有标签过程及源表不变。重新部署会替换本方案同名过程；业务表用 `if not exists` 保留数据，不自动迁移已经存在的异构表。若二次部署前发现列定义不一致，先处理结构差异，不能用重复建表掩盖问题。

分类规则使用存储过程内部的内联 `case` 表达式，不创建存储函数，不需要为此修改二进制日志或全局权限配置。

## 历史首算

先完成部署，然后在第2段中填写截止日。以下是假设已经确认 2026-10-09 数据完整的例子：

```sql
call dws_datasync.sp_product_role_history(
    'bootstrap','2026-10-09','dwd_datasync',
    null,null,null,null,null,null,null,0,50000
);
```

首算分两阶段扫描：先按年度、每次最多 50,000 个主键确定历史身份和起点，再按年度去重、合并经营指标。一次只保留一个年度的日级窄临时表，跨年度仅保留周期聚合，跨年段不会截断。年度表仍可能有数百万行，首算会占用临时磁盘并扫描历史两遍，建议低峰期运行；减少主键批大小只能控制读取批次，不能把年度临时表的总容量降为单批容量。

每个产品的历史与主导汇总在同一事务中写入，运行表的 `published_products` 同步递增。发生异常时，已经提交的完整产品保留，当前产品回滚。以相同截止日重跑首算，已处理到该日的产品跳过，其他产品继续；身份发现阶段仍需读取源数据。客户端断连可能留下 `running` 记录，结合连接状态确认，重新调用会创建新的运行记录；互斥锁会在连接结束后释放。

首算不是强制清空历史。完成段已经存在时仍复用；修正已完成段应使用指定区间重算，不应靠重复首算覆盖。

## 日常增量

更新版本时执行完整 SQL 第1段，更新加载器、核心计算及无参数定时入口三个过程；已有表及结果保留。这次不需要重新首算或重新迁移。定时任务之后只需执行：

```sql
call dws_datasync.sp_product_role_history_incremental();
```

定时入口自动读取产品表现续表最新日期。全部结果都已处理到该日期、且没有已保存首次观测日的待核身份需要初始化时，返回 `skipped / already_current`；有产品落后、截止日为空，或旧策略的待核空历史现在可以确定起点，则调用核心增量过程。按所有产品的最小、最大截止日共同判断，避免仅比较最大日期而漏掉失败后尚未更新的产品。源表为空、最新日期仍为北京时间当天或未来、源日期早于已有结果时分别跳过，不推进结果或倒退截止日。首算／导入初始化必须已经完成。

原增量过程读取每个产品的截止日和未完成段起点，复用冻结节点；漏跑时补齐新完成段及当前尾段，同时发现历史或 Listing 新商品。定时入口在源日期相同且没有可初始化旧待核身份时跳过，因此同日新增 Listing 通常等下一次源日期推进后加入。需要同日补入新身份时，仍可显式调用核心 `sp_product_role_history('incremental',...)`；已冻结期间的表现数据回补需指定重算。

近期读取先使用日期索引一次获取本次范围内的主键，再按临时主键范围分批回源，避免每批对整个日期范围重新排序。正常单年度增量复用身份发现阶段的去重明细，仅读取一次最近范围；跨年或长时间漏跑时逐年加载。年度临时表用 `truncate` 清空，产品发布的小临时表复用；两种清空均发生在单产品发布事务之外。完整MSKU仍参与最终身份匹配，临时索引前缀不作为身份截断依据。

缺失站点日先按周期计算应有日数，再减去实际观测日数，避免逐产品逐日回查日级表。应有日数由每年日历的累计数相减，使用两次日期主键查找，避免每个周期反复扫描多年日历；全局缺失日仍计 0，周期观测不足仍不计票。增量直接复用已冻结的原生历史数组，只替换原未完成尾段并合并新周期；主导角色仍从合并后的全部历史重新计票。需要组装多个新节点或重建历史时，通过按周期排序的 JSON 路径提取原生节点，避免窗口查询重复物化整套数组；不把经营 JSON 转成文本再解析，以保留原生数值类型和冻结节点内容。仅路径列表使用 `group_concat`，会临时提高本连接的长度限制，并在成功或失败后恢复原值。

完成首算且所有产品已推进至当前年份后，正常增量从最早未完成段读取，不扫描全部 2020—2025 年表。若最早尾段本身跨年，仍需读取跨年涉及的年度；若首算中断留下旧截止日，增量可能读取尚未补齐的年份，这是恢复历史的必要成本。脚本的日期筛选直接作用在原始 `start_date` 上，避免对列使用日期函数破坏索引范围访问。

存量静默商品仍保留，会生成缺失数据段，不删除商品，也不将缺失段算成问题产品。有近期记录的新商品会加入。按用户进一步确认，有日级表现记录后，有效 Listing 日期可以确定起点，不要求先有正销量或正库存；有记录且销量为 0 的周期仍按现行规则计算问题角色。只有 Listing、没有表现记录的身份仍保留候选日期和待核状态。

2026-10-12 用户确认的两类待核处理：有 Listing 候选日期而此前无表现记录的，沿用上面的处理；有表现记录但没有可用上架日期的，以 `first_observed`（最早产品表现记录日）作为起点，来源记为 `first_performance_record`，不再等待正库存或销量。此处的日期取源记录日期，零库存／零销量本身不排除该记录。

升级后首次增量会恢复旧结果中保存的待核身份及最早观测日，即使当前 Listing 已消失、近期没有记录，也初始化其空历史。源日期没有推进时也能完成这一次初始化，健康的同截止日产品整行不变。2026-10-12 只读核对的第二类全站点身份为 449 个，最早观测年度分布为 2020 年 5 个、2022 年 1 个、2024 年 161 个、2025 年 219 个、2026 年 63 个；对应国家身份为 1,327 个。这里没有既存周期结果可复用，需要一次性读取所需历史事实，不能用空历史推断每一天的销量或库存。加载器只将所需产品／日期落入临时明细，但年度表缺日期索引时仍须分页读取历史源表；本次补齐不承诺普通日常增量的 10 分钟耗时。补齐后已完成段冻结，后续继续近期增量，不重复补算这批历史。

此前待核的产品后续确认起点时，不再要求重跑整库 `bootstrap`。其周期仍从真实起点补齐，但源读取下界取已保存与本次发现的首次观测日期，保留旧的首次观测事实；观测前没有数据的段指标为空并标记缺失，不补造零销量。已有起点的产品仍只重算未完成段和新增段，旧完整节点保持冻结。若待核产品确实有更早的已知观测事实，则此次初始化会读取它所需的更早日期范围，这类一次性补齐可能比普通增量更久。冻结年度的历史明细回补仍需显式重算，不通过自动增量重新发现全部旧数据。

版本固定为 `history_30d_v47_20261010`。发现既有结果版本不同，普通首算/增量停止，先明确规则变更后的完整产品重建范围，再重新运行；不自动混用新旧分类规则。

## 指定产品与区间重算

填写完整的 `scope_mode + country_category + country + store + msku`。`business_unit` 的国家必须为空字符串；`country` 填真实国家。店铺填写现行规则标准化后的店铺名，MSKU 不截断。

局部重算的截止日必须等于该产品现存 `data_date`；第4段会读取它。需要推进截止日时，先增量，或者显式完整重建。例子：

```sql
call dws_datasync.sp_product_role_history(
    'rebuild','2026-10-09','dwd_datasync',
    '2026-08-01','2026-08-31','country','欧洲站','德国','shop','完整MSKU',0,50000
);
```

日期范围按上架锚点扩展至所涉及的完整 30 天段，例如选中周期内的两天，仍重算整个周期。范围外的历史节点保留，主导角色从更新后的历史重新统计。源读取会从最早涉及周期开始至该产品截止日，扫描该日期范围内的源记录，不保证只有指定商品的源行被读取。

需要修正起点时，完整重建该粒度产品：

```sql
call dws_datasync.sp_product_role_history(
    'rebuild','2026-10-09','dwd_datasync',
    '2020-01-01','2026-10-09','country','欧洲站','德国','shop','完整MSKU',1,50000
);
```

`reset_anchor=1` 必须从 `2020-01-01` 重建至截止日，重新判断起点并重新分段。真实起点可以早于 2020，早期没有源数据的段仍保留真实编号并标记不完整。国家站点与全站点为独立记录：同一源数据回补涉及两种粒度时分别重算；修正站点起点时先重建受影响国家，再重建对应全站点，保证最早站点起点一致。

规则版本升级应完整重建各受影响产品，不能只修一个局部段后把整条历史标成新规则。对该商品完全重建且保留既有起点时用 `reset_anchor=0`；同时需要更正起点才用 `1`。

## 表与 JSON

正式结果表为 `dws_datasync.dws_product_sales_role_history`，运行记录表为 `dws_datasync.dws_product_sales_role_history_run_log`。本次将正式表名改为英文，字段与计算口径保持一致；已有 opt 试跑表名保留。

业务表唯一键为 `(scope_mode,country_category,country,store,msku)`；全站点国家用 `''`。`data_date` 是已处理截止日，不按日追加整套快照。`created_time` 首次插入保留，`updated_time` 只在产品实际发布时更新。

| 独立字段 | 类型 |
|---|---|
| scope_mode | varchar(16)，business_unit / country |
| country_category | varchar(20) |
| country | varchar(100)，非空，默认空字符串 |
| store | varchar(100) |
| msku | varchar(500)，保留完整字符串 |
| data_date | date |
| created_time / updated_time | datetime(6) |
| evidence_json | json |

字符集和排序规则使用标签体系的 `utf8mb4 / utf8mb4_0900_ai_ci`。联合业务主键最大字符串字节为 2,944，小于 InnoDB 的 3,072 字节限制；临时去重表的完整身份键也在此限制以内。保留完整 MSKU 的含义是保留源字符串，比较规则沿用现有大小写不敏感排序规则。

| JSON 部分 | 核心字段 |
|---|---|
| identity | anchor_date、anchor_source、is_proxy、candidate_date、first_positive、date_conflict/reason、first_observed、anchor_status、asins、history_before_2020_missing |
| history | period_no、start/end、calculated_through、complete、role_id/role、sales_qty/amount、predict_gross_profit、daily_sales、margin_rate、small_rank/date、observed_days、stock_days、anomaly_days、missing_station_days、vote_eligible、exclusion_reason |
| dominant_role | role_id/role、counts、shares、share、valid_segment_count、excluded_segment_count、tie、max_count_role_ids、selected_latest_valid_period、tie_break |
| quality | source_history_start、segment_count、non_voting_count、interpretation、missing_is_not_zero_sales |
| calculation | rule_version、source_schema/tables、cutoff、last_mode、open_segment_start、frozen_completed_segments |

`margin_rate` 与 `shares` 存小数比例：0.15 表示 15%。现行标签证据的 `metrics.tag_margin_rate` 使用百分数，验收比较时已经乘 100。`counts`/`shares` 固定包含 star、potential、dog、problem；零有效样本时次数为 0，占比和主导角色为 null。

## 计算与异常口径

- 国家类别沿用 V47：英国→英国站；美国/加拿大/巴西/墨西哥→北美站；其他→欧洲站。店铺取名称第一个空格前部分，再取第一个连字符前部分。
- 商品身份沿用现行标签的占位 MSKU 排除规则：去掉首尾空格后，以 `amzn.gr` 或 `Amazon` 开头的记录不作为产品，前缀比较忽略大小写；有效 MSKU 本身仍保留完整原字符串。
- 商品池合并历史表现身份和当前有效 Listing 身份，既保留历史商品，也覆盖当前 Listing。只有 Listing 而无可核验经营事实的商品，保留候选日期及 ASIN，但不直接确定起点：`anchor_status=pending`、空历史、主导为 null。没有日期的有效 Listing 同样保留；候选日期按国家隔离，避免跨国串入。
- 候选起点取可解析的 Listing 日期或表现表 `product_create_time` 的最早值；没有可用日期时，以最早表现记录日替代，库存／销量全零也可以确认。若候选日期晚于首次正库存/销量事实则弃用，以该经营事实日替代，记录冲突原因。没有 2020 年前事实时无法额外证明候选日期的真实性，证据字段保留这一来源约束；可通过显式起点重建修正。已有确定起点保持冻结。
- 年度归属为 2020—2025 分别只读对应年度表，2026 及以后只读当前续表。同一年度的重复同步按国家＋标准店铺＋完整 MSKU＋ASIN＋日期，取最新 `create_time`、再取最新 `id`。年度表日期重叠不重复求和；如果年度归属表漏数据、数据只落在另一张表，必须先核实归属并回补，脚本不擅自跨表补造。
- 同日多个 ASIN 的经营指标累计到产品；有货日按该国家产品当天至少一个 ASIN 的 `afn_fulfillable_quantity>0` 判断，全站点按至少一个国家有货判断。库存只影响计票资格，不改变分类阈值。
- 全站点分类 101—104、站点分类 1301—1304，内联分类表达式保持 V47 的边界和判断顺序。站点排名采用段内最新记录日，再按当天最新 `create_time/id` 选取；不把排名平均，不擅自改用最后一个有效排名。
- 完整段日销为销量÷30；尾段为销量÷已过去自然天数。毛利为累计预测毛利÷累计销售额，销售额不大于 0 时毛利率为 0。退款/负毛利按源值参与累计，不平均每天毛利率。
